# drive-implementation

`/drive-implementation <plan page URL>` works the tasks on a plan page that `/plan-implementation` wrote, keeping the page current, and drives the plan's PRs through review until a person merges or closes them.

The skill is deliberately thin. The plan page's `meta/guide` already owns the schema, statuses, questions, delivery, and handover, so the skill holds only how the owner likes implementation to run:

- Each code-changing task gets its own worktree and its own Claude agent, labelled by task so what the owner sees reads as the plan does.
- Every task is reviewed by a fresh subagent and fixed by its implementer, up to three rounds before the driver asks the owner.
- A reviewed task is merged onto its PR's branch in that PR's own worktree, and the task's worktree and branch are removed.
- A PR is driven from the time it opens until it merges or closes, by the `drive-pr` skill, with the plan page standing in for its session.

The driver makes every worktree itself with `wt` and leaves only the agent to the harness. Both used to be left to the harness, and a plan driven on another machine ended up with some work in worktrees and some not, under names each tool picked, so the owner couldn't tell which branch held which task. Claude Code's worktree-isolated subagents are a particular trap here: the `WorktreeCreate` hook routes them through `wt` (see `dot_claude/AGENTS.md`), but they get a branch named for the agent alone, cut from the default branch rather than the PR's branch. `wt` is in these dotfiles on every machine and puts every worktree in `.worktrees/`. The guide owns the names, so a project whose instructions say otherwise can still override how worktrees are made.

Cleanup takes `wt remove` and then `git branch -d` in the PR's worktree, because `wt remove` deletes only a branch merged into the main checkout's `HEAD` or the default branch, and a task branch is merged into its PR branch. `wt remove` removes the worktree first and then exits 2 over the kept branch, which is expected here, not a failure.

Driving a PR through review is its own skill, `drive-pr`, because carrying a PR through review is just as useful for a PR no plan made. The driver runs it in place of its defaults, so its questions go on the page, a fix runs through the same worktree, agent, and fresh-review cycle as a task, and each PR's `replies` field on the page says whether replies need the owner's confirmation. The owner chose `auto` as the default: fixes and replies happen without asking, and only behavior, scope, and steps only a person can take come to the page. A plan is `done` only once every PR has merged or closed, rather than at handover, so the page's status says whether anything is still in review. Driving starts when a PR opens rather than when it is marked ready, because a draft can fall behind its base as easily as a ready PR, and a driver isn't always allowed to mark one ready: auto mode refuses `gh pr ready`, which once left a finished plan's draft PR conflicting with nothing watching it. Marking it ready then becomes a person's step on the page.

A harness or its instructions can instead give each open PR its own agent running `drive-pr`, because the owner wants each PR visible and steerable in its own tab, as each task already is. That agent alone commits and pushes in the PR's worktree, and the driver hands it reviewed task branches rather than merging them, because two agents committing in the same checkout would trip over each other's index and working tree. Fixes for reviewers, checks, and conflicts go to it rather than through the driver's task cycle, because `drive-pr` already makes and reviews them. The skill names no harness commands for this; the drive protocol for each harness owns those. Without such an agent the driver works as before.

The page is updated as things happen, because it is the owner's main view of the work. The driver decides everything reversible itself and puts on the page only what is the owner's to decide, such as product behavior, scope, a PR split, or a step only a person can take. It stops only when nothing can move without an answer.

It is Claude-only, because comment watches and artifact databases are Claude Code features. It keeps no state of its own: the plan page is the record, and a resume reconciles the page with the worktrees, agents, and PRs. The driver has to be a main-loop session, because only one of those can watch an artifact for comments. A background subagent doesn't outlive its session, so a resumed run relaunches whatever was in flight.

What it relies on from the plan page: each task's `goal`, `approach`, and `verify` make the implementer's brief, with `touches` as a hint. The page shows `goal` on a task's collapsed card for people, so the brief reads it as the plain statement of what the task achieves and takes the detail from `approach` and `verify`. A task the driver marks `blocked` needs `blocked_on`, a sentence saying what it waits on, because that is what the collapsed card shows; the driver removes it when the task moves on. The guide defines both.
