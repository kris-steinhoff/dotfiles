# Scripts in ~/.local/bin

This file covers the reasons behind the scripts deployed to `~/.local/bin` that have notes, `ai-usage`, `github-review-queue`, and `wt`, so load it before changing any of them. Usage lives in each script's docstring and `--help`; this file holds why.

## ai-usage

`executable_ai-usage` shows usage for Claude, ChatGPT, and OpenRouter. It is a `uv run --script` Python tool that reads Claude Code's OAuth credential (`~/.claude/.credentials.json`, or the macOS Keychain) and Codex's ChatGPT credential (`~/.codex/auth.json`) and queries their respective usage endpoints. It adapts to the windows each account reports; `--service` (repeatable) limits the view to the named providers. On a terminal it refreshes live in place until Ctrl-C, with Ctrl-R forcing a refresh. `--once` prints a single snapshot and exits, `--json` emits raw payloads keyed by provider, and `--json windows` emits every service's windows (key, percent used, length, reset time, how far ahead of pace) and status in one shape for a script that compares them, without failing on a service it can't read.

Pace is computed here rather than in each caller, so the Herdr `ai-usage` mod and any later consumer agree on it. So is each window's color: `level` (`ok`, `warn`, `high`, or `danger`) colors the terminal view's bars and is reported in `--json windows`, so the mod colors its rings by the same rule rather than keeping a copy that drifts. It goes by pace: any amount ahead is `warn`, 10% of the window ahead or the limit itself is `danger`. A window without pace falls back to the provider's own severity where Claude reports one, then to the raw percent. Below a service's panel, each window ahead of pace gets a line saying how far ahead it is and how long until it's back on pace with no further use, so a yellow or red bar explains itself; it sits outside the panel so the table of bars keeps its shape. `ahead_of_pace` is how far a window is ahead of the even rate that reaches 100% exactly at the reset, as a share of its length (`used − elapsed share`): any amount ahead means on track to run out, and with no further use it is the share of the window until elapsed time catches up. It is a difference rather than a projection (`used / elapsed`), because a projection swings wildly while almost no time has passed and needed a warm-up during which a fast start went unflagged. It is measured when the script runs, not when the payload was fetched, so it stays current while the cache ages; a window with no fixed length or reset time (a credit balance, a monthly budget) gets `null`. The mod reads `used_percent`, `window_seconds`, `resets_at`, `label`, `ahead_of_pace`, and `level`, so changing their meaning breaks it.

OpenRouter is prepaid credits rather than a subscription, so its panel shows the account's balance, a bar per budget enforced on the key, and the key's spend today, this week, and this month. Its keys come from the environment, set machine-locally: `OPENROUTER_API_KEY` for the key's spend and budgets, and `OPENROUTER_MANAGEMENT_KEY` for the balance, because OpenRouter's balance endpoint accepts only a management key, which can also create and delete keys. Either one alone is enough, and a machine with neither hides the panel. Because sign-in can differ between callers when it comes from the environment, a missing credential is never written to the shared cache, so a caller without the keys can't hide OpenRouter from one that has them.

Every mode reads through a shared per-service cache in `~/.local/state/ai-usage/`, so any number of callers (a status line, several live views) can run as often as they like without adding requests: a caller fetches only when the last attempt is older than its `--interval` (default 600), and a file lock makes concurrent stale callers wait for one fetch rather than each making their own. Failed attempts are cached too, so callers back off from an error together; a 429's Retry-After binds even Ctrl-R, since forcing through it only draws another 429. The default is 10 minutes rather than 5 because Claude Code itself calls the same `/api/oauth/usage` endpoint, and Anthropic limits that endpoint per account: with several Claude sessions running, the total went over the limit and drew 429s with an hour-long Retry-After, even though ai-usage asked only once per interval. The cache holds the payload and the Claude plan name, never tokens. Run inside the Claude sandbox, it needs to reach `api.anthropic.com`, `chatgpt.com`, and `openrouter.ai` and to write that cache; `settings.json` grants all of them.

## github-review-queue

`executable_github-review-queue` lists one repository's open, non-draft PRs that request a review from me or one of my teams, excluding my own, as `{"items": [...]}`. `--all` prints every one with its state, `new` or `reviewed`, and `--ready` prints only the new ones. It is a stdlib Python script that runs on macOS's `/usr/bin/python3` (3.9), so it works inside the Claude sandbox, and it depends on nothing in the `github-pr` skill. Its tests are `tests/test-github-review-queue`, run from the source directory against a fake `gh`.

- **No state of its own.** Whether a PR is done is read from GitHub: a PR is `reviewed` when one of my recent reviews names its current head commit and is an approval, a change request, or a comment with a body. A lone thread reply doesn't count, though GitHub records it as a review too. It is read per PR through GraphQL, because `gh pr list` returns only a PR's first hundred reviews. A PR pushed since my review is new again, and a review whose commit GitHub reports as null, which happens after a force-push, counts as not at the head.
- **The costs of keeping no state.** Three are accepted. A PR whose author answers the review without pushing stays done until review is requested again at a new head. A PR finished without posting comes back as new in another session. And nothing marks a PR as taken: the Herdr reviews tab finds an existing session for a PR by its labels, so it doesn't start a second one, but two agents working the queue by hand could still both review the same PR.
- **The Herdr reviews mod depends on its output.** The mod (`dot_config/herdr-app/mods/reviews/`, notes in `dot_config/herdr-app/AGENTS.md`) calls it with `--all` and reads `number`, `title`, `url`, `author`, `created_at`, `size` (`additions`, `deletions`, `files`), `stacked_on`, `jira_keys`, `state`, and `other_reviewers`, so renaming or changing the meaning of any of those breaks the mod. `base_branch`, `head_branch`, and `head_sha` stay for other callers. The test that checks each item's exact key set guards this contract.
- **`other_reviewers`** lists the logins of everyone except me, the PR's author, and bots who has a review that counts by the same rule as mine, at any commit. Bots are left out because review bots such as Copilot comment on nearly every PR, so counting them would mark almost everything as already reviewed. It reads each person's last 100 reviews and also their latest approval or change request, since thread replies can push an older approval out of those 100.
- **`stacked_on` ignores forks.** It is the open PR whose head branch is this PR's base, but only among PRs from this repository. A fork's head branch lives in the fork, so a fork's PR from its `main` would otherwise look like the PR under every PR based on `main`.
- **`jira_keys`** come from the title and the upper-cased head branch, so a branch named `nxc-162-household-editing` yields `NXC-162`.

## wt

`executable_wt` creates, lists, switches to, and removes git worktrees, so people, agents, and skills share one behavior. `wt add` makes a worktree for a branch (creating the branch if needed) under `.worktrees/` in the repo's main checkout, `wt list` shows the main checkout and those worktrees, `wt switch` prints an existing one's path, and `wt remove` removes one and deletes its branch when merged. The zsh wrappers `wta`, `wts`, `wtr`, and `wtl` in `dot_config/kris-steinhoff/zshrc` call it.

- **One place for worktrees.** Every worktree lives in `<main checkout>/.worktrees/`, hidden from `git status` by a line in the common dir's `info/exclude`, so manual and agent-made worktrees sit together inside the folder a Claude session started in the repo can already write. `list` and `remove` deliberately ignore worktrees elsewhere, such as those other tools make.
- **Finding the main checkout.** It is `core.worktree` from the common dir's config when set, else the first `git worktree list` entry, because in a submodule that first entry is the git folder under the parent's `.git/modules`.
- **No upstreams.** No branch `wt` creates records an upstream (`--no-track`), because recording one writes `.git/config`, which Claude's sandbox blocks. `push.default=current` in the shared gitconfig keeps a plain `git push` working without one. By default a new branch starts from a freshly fetched `origin/<default>`, or from `origin/<branch>` when the remote already has that branch, and `--base` overrides both; a failed fetch warns and continues from the last fetched state, so it works offline.
- **Its own merged check.** `remove` deletes a branch only if it is an ancestor of the main checkout's `HEAD` or of `origin/<default>` as last fetched. Plain `git branch -d` compares a branch with no upstream only against the main checkout's `HEAD`, so it refused even untouched branches whenever local main was behind. Squash merges still count as unmerged.
- **Never forces.** A dirty worktree or unmerged branch is kept: `wt` prints the exact force command (`--force --force` for a locked worktree) and exits 2, so losing work always takes a separate, deliberate step.
- **Output shaped for the wrappers and agents.** In human mode, `add` and `switch` print only a path on stdout, because `wta` and `wts` cd to it; everything else goes to stderr. `switch` only finds existing worktrees, and includes the main checkout so `wts` can go back to it. `wta`, `wts`, and `wtr` exist only because a script can't change its caller's directory. Exit codes are 0 success, 1 error, 2 refused; usage errors, which typer exits 2 for, are mapped to 1 so 2 always means refused. `--json` prints exactly one object per line, even on error, for agents to parse; the exception is a usage error, which exits 1 with typer's message on stderr and no JSON.
- **No hangs, no odd branches.** Git runs with `GIT_TERMINAL_PROMPT=0` so an agent never waits on a credential prompt. `wt add origin/foo` (any configured remote's name as a prefix) is rejected when no local branch has that name, because it would create a local branch literally named `origin/foo`.
- **Per-repo setup through git config.** The command to run in a new worktree (installing dependencies, say) is `git config wt.setup`, so it can be set per clone, or for many repos at once from the shared gitconfig with a conditional include. It runs with `sh -c` in the new worktree, and a failure only warns and keeps the worktree. For example, with `[wt] setup = npm ci` in `~/.config/git/acme.gitconfig`:

  ```gitconfig
  [includeIf "hasconfig:remote.*.url:git@github.com:acme/**"]
  	path = ~/.config/git/acme.gitconfig
  ```

- **Sandboxes.** A Claude session in a linked worktree can write its main repo's `.git` (commits, refs, the index), but `.git/config` and `.git/hooks` stay read-only, which is why `wt` never writes config. Codex protects a checkout's `.git` and a linked worktree's resolved git dir, so there `wt add` and `wt remove` go through Codex's scoped escalation like any git write. `wt` replaced the `worktree-layout` skill, whose clone-per-stream layout needed an unsandboxed setup step.
- **Moving a worktree breaks builds.** Anything a worktree built, such as a virtualenv, keeps absolute paths, so rebuild it after a `git worktree move`.
- **Other tools' worktrees.** Claude Code's `WorktreeCreate` and `WorktreeRemove` hooks hand its worktrees to `wt` (see `dot_claude/AGENTS.md`). The Herdr app is left on its own `~/.herdr/worktrees/<repo>/<branch>`, a constant at the top of its shipped `worktree` mod (New worktree in the space and + menus). A clone of that mod could run `wt add` instead, but it wasn't worth it while `wta` in a terminal does the job; the terminal Herdr's `worktrees.directory` setting couldn't do it either, since it names one central folder for every repo. Orca isn't configured, because it wasn't installed on the machine where this was set up. The desktop app's Code tab has its own worktree location setting, in its Settings under Claude Code, which only the user can change.
- **A uv script, not zsh functions.** As a `uv run --script` typer program, agents and other shells can call it the same way people do. The first run on a machine needs network to fetch typer.
