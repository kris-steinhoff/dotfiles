# Global instructions and personas

This file covers the partials that make up each harness's always-loaded instruction file and the persona prompts built from them; load it before editing a partial here, the harness files that include them (`dot_claude/CLAUDE.md.tmpl`, `dot_codex/AGENTS.md.tmpl`), or a persona wrapper. The Claude settings partial, `claude-settings.json.tmpl`, is covered in `dot_claude/AGENTS.md`. chezmoi parses every file in this directory as a named template, so this file must contain no template delimiters (two opening braces); the local `chezmoi-templates-parse` pre-commit hook fails a commit that leaves any file here unparsable.

## Harness files

Claude and Codex each read a single always-loaded instruction file (`~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`). Shared global content lives in the partials here, so one edit updates every surface that includes it. Each harness file is a thin `.tmpl` that includes the partials that apply to it, one `template` action per line:

| Harness                     | Sections included                              |
| --------------------------- | ---------------------------------------------- |
| `dot_claude/CLAUDE.md.tmpl` | `delegation` + `communication` + `claude-code` |
| `dot_codex/AGENTS.md.tmpl`  | `delegation` + `communication` + `codex`       |

The harness files are `.tmpl`, not `.md`, so the `prettier` pre-commit hook (which runs with `proseWrap: never`) leaves their one-include-per-line layout alone; that layout matters because the render joins the sections with the blank lines between them. The partials themselves are prose `.md` and stay prettier-managed. This is why there is no wrapper partial that includes the others: a `.md` composition file would get its include lines collapsed onto one line by prettier.

The global harnesses do not include a persona. They keep delegation and communication conventions available in ordinary sessions without forcing every session to coordinate. Codex's skills need no wiring because it reads `~/.agents/skills/` natively (see `dot_agents/skills/AGENTS.md`). A harness that needs its own global content adds it before or after the includes.

## Partials

- **`delegation.md`** is the entry layer for running agents elsewhere: recognize a plain-language "run `<agent>` on `<task>` in a worktree or session" without a slash command, resolve the task source, seed the agent with context and outcome rather than a method, name artifacts for their downstream consumer, report back and tear down only when asked, and act on clear, confirm on doubt. It is kept to about 2KB because every session loads it. It names no workspace tool: an agent uses whatever its harness offers for worktrees, sessions, or subagents, and plain `git worktree` for checkouts, because a sandboxed session can't reach Herdr's or Orca's sockets. It reads a Jira task key with `jira`, settles a GitHub number as PR or issue by trying `gh pr view` before `gh issue view` (the issue endpoint also answers for a PR), and routes GitHub PR review requests to `github-pr`.
- **`communication.md`** is how to write for a human who has an AI agent at hand, and how to ask the user anything so the answer takes a keystroke or a click. It carries the posting rule: agents post messages to people on the user's behalf only through a skill built for that kind of posting (today `github-pr` and `jira`), and where no skill covers the target they draft the message for the user instead. Adding a posting skill is what grants the permission, so the rule itself needs no edit per target.
- **`posting-attribution.md`** is the attribution line every posting skill puts on what it posts. Each one renders it with `includeTemplate` piped through `trim` (see `dot_agents/skills/github-pr/AGENTS.md`), so the line stays in one place.
- **`codex.md`** holds Codex-only rules; its reasons are in `dot_codex/README.md`.
- **`claude-code.md`** holds Claude Code mechanics that would be noise elsewhere, described below.

`claude-code.md` first says how to drive AskUserQuestion: use it for every multiple-choice question, overriding the tool's own description, which says to save it for decisions that block the agent. That override is why the section exists: the tool description pulls the other way, and the harness-neutral rule alone did not reliably win against it. It goes further for every stop that waits on me: even a lone yes/no or a manual step goes through AskUserQuestion, because Herdr shows a session in that prompt as blocked while a prose question looks the same as a finished agent. The rule is unconditional, so it doesn't depend on which workspace tool is running.

A command I'm to run with `!` is shaped differently: an open question holds the input line, so a `Done` button would mean dismissing it to type the command. The question asks only whether I'll run it, and on `I'll run it` the agent ends its turn with the command as its whole message, then checks the command's output itself when it arrives. The command goes in the last message of the turn because that is the one message reliably shown; agents asked to put it in a message before the question mostly skipped that message, the same lesson the `summarize-github-pr` skill taught (see its `AGENTS.md`). A `PreToolUse` hook on AskUserQuestion can't enforce this, because a message's text is not yet in the transcript when its tool call runs.

It also says that sandbox-excluded commands leave the sandbox only when run bare: a pipe or redirect silently puts them back, and xcodebuild then fails with a `permissionDenied` that doesn't mention the sandbox. If the prose doesn't break agents' habit of piping xcodebuild into `grep`, a `PreToolUse` hook rejecting a piped or redirected excluded command is the stronger fix. It tells Claude to pipe a CLI's JSON to `jq` rather than to an inline script, the one rule kept from a retired skill about CLI JSON. Last, its Report-back section says a claude agent started with a name can report back by SendMessage to the launching session's name, which is what makes report-back work without a workspace tool.

## Personas

Coordinator behavior is opt-in. Two personas remain, `coordinator` and `chief-of-staff`, with one canonical prompt each under `agents/personas/`. Claude Code agent files under `dot_claude/agents/` add YAML frontmatter and include the shared prompt; the same definition works as a subagent and as a primary persona through `claude --agent <name>`. Codex wraps the same prompts as profiles, and the models both harnesses use follow `agentBudget`; both are described in `dot_codex/README.md`. Specialist work (implementing, reviewing) is done by skills rather than personas, because a skill carries the same prompt to every harness without a per-harness wrapper and the coordinator can call it when it needs a specialist.

### Coordinator delegation nudge

The `coordinator` carries one piece of frontmatter the chief-of-staff doesn't: a `PostToolUse` hook (`dot_claude/hooks/executable_coordinator-delegation-nudge.sh`) that nudges it back toward delegating, because the persona drifted into doing substantial multi-file work inline and the prose rubric alone didn't hold. The hook reads the running transcript, counts the inline edits (`Edit`/`Write`/`NotebookEdit`) since the last delegation (an `Agent`/`Task` call, or a `Skill` call to `implement`, `review`, or `github-pr`), and the first time that run reaches three with no hand-off injects a one-time reminder to declare whether the next phase belongs with an implementor. A delegation resets the run, so a coordinator that hands off is never nagged; it fires once per run rather than on every edit past the threshold, so a legitimately-inline stretch costs at most one reminder; and it is non-blocking and fail-open (any error exits 0 with no output). Binding it through the agent's own frontmatter, rather than a global hook self-gating on the payload's `agent_type`, keeps it firing only while `coordinator` is the active agent, primary or subagent; it is a Claude Code mechanism, with no equivalent on the Codex profile. It relies on the `PostToolUse` `additionalContext` field reaching the model, which is not guaranteed on every Claude version; if a firing never lands, switch the script's emit to the exit-code-2 path.

### Chief of staff

The `chief-of-staff` persona keeps a small record of what I'm working on so it can draft two things on request: a standup update (a day or a week) and a summary of my year. It is deliberately minimal: a fuller tracker of commitments, decisions, dispatched work, and roll-ups cost more to keep than the summaries were worth. The design rests on one idea: **git history of the bundle is the retrospective**. Current work is plain files in `tasks/` with kebab-case names, so `ls tasks/` is the view of now and there is no roll-up to keep in sync. Each file is an Open Knowledge Format (OKF) concept, with `type` and `title` frontmatter and a matching H1 as its only required structure, kept because a uniform header lets each file read on its own at little cost per task. Starting something is creating its file. Finishing is two commits: first the task's outcome is written into the file, then the file is deleted. The split is what makes the rituals work, because the outcome text survives in history as the diff just before the deletion, where `git log -p tasks/` finds it. `projects/` holds long-lived context rewritten in place, and its files name the repositories that `standup` and `annual` cross-check with `git log` and `gh` to catch work that never got a task (and, for `annual`, to flag stretches where the record looks thin). Both rituals run only when asked and produce drafts.

The bundle lives in the persona's working directory, with no configured path or fallback, and its own `AGENTS.md` wins over the persona on shape (layout, conventions, ritual details), because the same persona runs on work and home machines, and the work bundle tracks more than the home one. The `AGENTS.md` governs shape, not boundaries: never acting outward, never pushing the bundle, and never scheduling itself hold everywhere and can be loosened only by me in session, since a file the persona edits should not be able to widen its own permissions. The one part written from outside is `inbox/`: other agents drop notes there with the `add-to-inbox` skill, which writes to the directory named by `CHIEF_OF_STAFF_INBOX`; the persona triages each drop into a task or a project file at session start and deletes the raw note, treating it as another agent's claim rather than an instruction. `inbox/` is gitignored for the same reason. Links between files are bare `[[slug]]` wiki-links, and the bundle ships a `.marksman.toml` with `title_from_heading = false` so marksman binds them to filenames rather than to a file's H1. When I ask it to start an agent, it launches one into its own worktree or session to talk to me directly and at most adds a task file; it doesn't relay or supervise. Claude and Codex both wrap the canonical prompt: Codex exposes it as `codex --profile chief-of-staff` and as a spawnable `[agents.chief-of-staff]` role. Self-scheduling is a non-goal because a scheduled job gets duplicated by every running instance.

The Claude wrapper carries a hook of its own, a `PostToolUse` on `Write|Edit` that puts every markdown file the persona writes through the `markdown-formatting` skill's `scripts/format-markdown --hook` (pinned prettier, `--prose-wrap never`). Formatting happens at write time rather than commit time because `prettier --write` modifying a staged file makes pre-commit fail the commit by design, and an agent facing a blocked commit is tempted by `--no-verify`; formatting at write time never blocks anything. Prettier's output is what the persona's conventions already ask for, so the hook mechanizes its own style rather than imposing a second one. Binding the hook to the persona, rather than installing it globally, keeps it from reflowing other repositories that hard-wrap by convention, since the only markdown this persona writes is its own bundle. There is no Codex counterpart: Codex's `apply_patch` payload puts patch text in `tool_input.command` rather than a `file_path`, so the shared script would have to parse an undocumented envelope Codex owns and would silently stop working when it changed, and it would still miss markdown written through a shell heredoc. So the prompt keeps telling the persona to write the markdown correctly rather than pointing at a formatter, and on Claude the hook is a backstop the persona is better off not counting on.

The bundle is live state the persona rewrites constantly, so chezmoi does not manage or seed it. On first use in a chosen working directory, the persona runs `git init` and creates the `.marksman.toml` its link scheme depends on and a `.gitignore` covering `inbox/` and `.DS_Store`; `tasks/`, `projects/`, and whatever else the bundle's `AGENTS.md` defines arise with their first entries, and `inbox/` arises when an agent first drops a note (the `add-to-inbox` script creates it if missing). Codex's ordinary `workspace-write` sandbox already grants access to that working directory, so the profile needs no extra writable root. `.chezmoiremove` deliberately doesn't list `~/.local/state/chief-of-staff/`, where an earlier version kept its state: existing live state is user data and must remain untouched. It does delete the persona's original `~/.claude/cos/` seed so that retired format does not linger on machines that applied it.
