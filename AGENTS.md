# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a personal dotfiles repository managed with [chezmoi](https://chezmoi.io/). This repo is the chezmoi source directory — files use chezmoi naming conventions (`dot_` prefix for dotfiles, `executable_` prefix for scripts) and are applied to `$HOME` by chezmoi.

## Bootstrap

To set up a new machine:

```bash
chezmoi init kris-steinhoff/dotfiles
chezmoi apply
```

`chezmoi init` clones this repo to `~/.local/share/chezmoi`. `chezmoi apply` copies managed files to `$HOME` and runs `run_once_bootstrap.sh`, which:

1. Ensures `~/.zshrc`, `~/.config/git/config`, and `~/.vimrc` each source/include the shared config files under `~/.config/kris-steinhoff/`
2. Runs `brew bundle install` from `~/.config/homebrew/Brewfile` if Homebrew is available
3. Runs `nvim --headless "+Lazy! restore" +qa` to install Neovim plugins at the commits pinned in `lazy-lock.json`

## Neovim plugin pinning

`dot_config/nvim/lazy-lock.json` is checked in. lazy.nvim installs plugins at the commits recorded there, which guards against supply-chain compromise of upstream repos. The bootstrap step above installs from the lockfile rather than letting plugins float to HEAD.

When updating plugins:

1. Run `:Lazy update` inside nvim.
2. Review the diff in `~/.config/nvim/lazy-lock.json`.
3. `chezmoi re-add ~/.config/nvim/lazy-lock.json` to pull the new commits into the source dir, then commit.

Without step 3, the next `chezmoi apply` will revert the lockfile to whatever's checked in.

## Claude Code settings.json

Other tools write into `~/.claude/settings.json`. Orca and Herdr each install their agent-state hooks there (Orca's alone span about fifteen hook events), and Claude Code adds keys of its own, such as a flag recording an accepted prompt. A plain template wiped all of that on every apply, so the source is a `modify_` script, `dot_claude/modify_private_settings.json.tmpl`, like the one for Codex's `config.toml` described below. The settings we manage live in the partial `.chezmoitemplates/claude-settings.json.tmpl`, which the script embeds. The script reads the live file and writes the partial merged over it. A top-level key in the partial replaces the live value wholesale, and a live key the partial lacks is kept. Hooks merge per hook group: a group that runs any managed command is replaced by the managed groups, and every other group belongs to another tool and stays, after ours. The script tells a group apart only by its commands, so a hook taken out of the partial goes into its `RETIRED_COMMANDS`; otherwise it would linger as another tool's. It is plain Python with no dependencies, because macOS's own `python3` is enough and uv adds nothing here.

Herdr's own `SessionStart` entry is one of those kept groups. These dotfiles used to manage a copy of it with a `~` path, which Herdr's install didn't recognize as its own, so the live file ended up with two. The managed copy is retired, and Herdr owns its entry outright.

Claude Code also rewrites the file in its own key order whenever it changes something internally (e.g. saving a permission), so both sides are kept in `jq -S` order:

- The partial must render in `jq -S` order, which the local `sort-claude-settings-json` pre-commit hook checks by rendering it with `chezmoi execute-template`. It checks rather than fixes, because a template isn't JSON that `jq` can rewrite. The script's output is in the same order.
- `~/.claude/settings.json` (the live file) is kept sorted by a `ConfigChange` hook, `dot_claude/hooks/executable_sort-settings-json.sh`, which re-sorts it with the same `jq -S` after every change.

A `chezmoi apply` diff on this file should therefore only mean a real value changed.

The partial is a template for one reason: a machine can add its own sandbox write paths. A list named `claudeSandboxAllowWrite` under `[data]` in the machine's chezmoi config is appended to `sandbox.filesystem.allowWrite`. This is how a work project's paths reach the sandbox without being written into these dotfiles, for example a beads database in a project folder that sessions in every clone and worktree need to lock. User settings are the right level for that rather than a project's `.claude/settings.local.json`, because a worktree session loads its own checkout's settings, not its clone's. `.chezmoi.toml.tmpl` carries the list forward, so a later `chezmoi init` doesn't drop it.

## Codex config.toml machine-local state

Codex rewrites `~/.codex/config.toml` at runtime and injects machine-local state that must not be version-controlled: `[projects.*]` trust levels (per-machine checkout paths), `[tui.*]` UI counters, and `[hooks.*]` trusted hook hashes. A plain template would clobber that state on every apply and force re-trusting projects and hooks.

So the source is a chezmoi `modify_` script, `dot_codex/modify_private_config.toml.tmpl`, rather than a static template. A `modify_` script receives the current target on stdin and its stdout becomes the new file. The script is a `uv`-run Python program that parses the live file with `tomlkit`, sets only the settings we manage (`model`, `project_doc_fallback_filenames`, `approval_policy`, `approvals_reviewer`, `[features]`, `[sandbox_workspace_write].writable_roots`, `[agents]` — the last templated on `agentBudget`), and dumps the document back. Because `tomlkit` preserves the layout of everything it does not touch, Codex's machine-local tables round-trip verbatim, applies are idempotent (a clean machine shows no diff), and nothing is silently dropped whatever new keys Codex may add. This needs `uv` present at apply time (it is in the Brewfile); the earlier `awk`-based version avoided that dependency but classified sections by regex and could drop unknown top-level bare keys.

The shebang pulls `tomlkit` via `uv run --with tomlkit`, not PEP 723 inline metadata (`--script`). This matters because `uv run --script` keys its ephemeral venv on the script's file path, and chezmoi runs a `modify_` script from a fresh temp path on every apply — so that env never hit the cache and uv reinstalled the dep (printing `Installed 1 package`) on every `chezmoi apply`. A `--with` env is keyed on its requirements instead, so it survives the changing paths and uv only rebuilds (and reports) it on a cold cache or a dep bump. The tradeoff is that this script alone differs from the PEP 723 pattern `ai-usage` uses.

The filename attribute order is `modify_private_` (type prefix before the `private_` permission attribute); `private_modify_` is not recognized and chezmoi treats the leftover `modify_` as a literal filename.

## Herdr app settings

The Herdr desktop app (`herdr-app`) keeps its whole interface as files in `~/.config/herdr-app/`, and its Settings screen writes `settings.json` itself (zoom, appearance, contrast, telemetry). So that file's source is a chezmoi modify-template, `dot_config/herdr-app/modify_settings.json`, which reads the live file and sets only the keys we manage, as the `modify_` scripts above do; it needs no interpreter because chezmoi's own `fromJson` and `setValueAtPath` are enough. The app ships no Tokyo Night, so `themes/tokyo-night.json` is ours; the app leaves theme files it didn't write alone. Keys stay on the app's defaults, and the shipped layouts and mods are left unmanaged, because Herdr replaces them on every start and personal changes to them go through clones. The older terminal Herdr's `~/.config/herdr/config.toml` is a separate program's config and stays as it is.

## Config architecture

Shared configs live under `dot_config/kris-steinhoff/` (deployed to `~/.config/kris-steinhoff/`) and are _included_ by the machine-local config files (not replaced). This lets local overrides coexist with the shared baseline:

| Shared file                          | Included by            |
| ------------------------------------ | ---------------------- |
| `~/.config/kris-steinhoff/zshrc`     | `~/.zshrc`             |
| `~/.config/kris-steinhoff/gitconfig` | `~/.config/git/config` |
| `~/.config/kris-steinhoff/vimrc`     | `~/.vimrc`             |

The `run_once_bootstrap.sh` script uses `ensure_config` to add the include line automatically, prompting the user when a file already exists but doesn't include the shared config.

## Agent skills

A skill is authored once and shared across every agent surface, so its content is edited in exactly one place. The canonical copy is a real directory under `dot_agents/skills/`, which deploys to `~/.agents/skills/`.

Each skill directory follows the [agentskills.io](https://agentskills.io/specification) format: a required `SKILL.md` with `name`/`description` frontmatter, plus optional `scripts/` (executable code), `references/` (documentation loaded on demand), and `assets/` (templates, static resources) subdirectories.

That location is the cross-agent convention, not an arbitrary pick. Codex and OpenCode both read `~/.agents/skills/` natively, so they use the canonical copy as it is. Claude Code looks elsewhere, so it gets its own entry for the skill that is rendered from the canonical one.

The canonical file is `SKILL.md.tmpl`, a template, because the harnesses do not agree on frontmatter. Claude Code understands fields such as `context: fork`, `model`, and `disallowed-tools` that other harnesses ignore or choke on, and the right values (the model, for one) depend on the machine's `agentBudget`. So the canonical frontmatter holds only `name` and `description`, and ends with a hook that splices in whatever extra lines the including template supplies:

```
{{- with get . "custom" }}
{{ . }}
{{- end }}
```

Each surface then sees only the fields it should:

| Surface         | Source path                                  | Frontmatter                          |
| --------------- | -------------------------------------------- | ------------------------------------ |
| Canonical       | `dot_agents/skills/<name>/SKILL.md.tmpl`     | `name`, `description`, and no extras |
| Codex, OpenCode | none, they read `~/.agents/skills/` natively | same as canonical                    |
| Claude Code     | `dot_claude/skills/<name>/SKILL.md.tmpl`     | canonical plus Claude-only fields    |

A Claude entry with nothing extra is one line that renders the canonical template:

```
{{- includeTemplate "dot_agents/skills/<name>/SKILL.md.tmpl" . -}}
```

A Claude entry with extras builds the lines first and merges them into the context, which is how the model follows `agentBudget`:

```
{{- $model := ternary "opus" "sonnet" (eq (get . "agentBudget") "generous") -}}
{{- $custom := printf `context: fork
agent: general-purpose
background: false
model: %s` $model -}}
{{- includeTemplate "dot_agents/skills/<name>/SKILL.md.tmpl" (merge (dict "custom" $custom) .) -}}
```

`includeTemplate` takes its path from the source directory root, like `include`. Claude-only fields never go into the canonical frontmatter; they live in the Claude entry.

Everything in a skill directory other than `SKILL.md` (`scripts/`, `references/`, `assets/`, or other loose files) is not templated. Each Claude entry directory gets a `symlink_<entry>.tmpl` per such file or directory, whose entire body is the link target:

```
{{ .chezmoi.homeDir }}/.agents/skills/<name>/<entry>
```

The executable bit lives only on the canonical copy (the `executable_` prefix is dropped from the link name), so a script is never duplicated. A `symlink_` entry sitting where chezmoi used to apply a whole-skill symlink converts to a real directory on the next apply, so no `.chezmoiremove` entry is needed for that move.

A skill's Python scripts must run on the `python3` that agents actually get, which inside the Claude Code sandbox is macOS's own `/usr/bin/python3`, 3.9. A script that runs on 3.9 keeps the plain `#!/usr/bin/env python3` shebang; `X | None` in an annotation needs `from __future__ import annotations` for that. A script that needs anything newer, such as `tomllib` (3.11), runs through uv instead: `#!/usr/bin/env -S uv run --script` with a PEP 723 block declaring `requires-python = ">=3.11"`, so uv supplies an interpreter it already has. Its path is stable, so uv's cached environment is reused across runs, unlike the `modify_` script described below.

To add a skill:

1. Write `dot_agents/skills/<name>/SKILL.md.tmpl` with the hook above, using `chezmoi add` for any scripts (it applies the `executable_` prefix to nested scripts such as `scripts/` helpers, which a manual copy would miss). This alone is enough for Codex and OpenCode.
2. Create `dot_claude/skills/<name>/SKILL.md.tmpl` with the `includeTemplate` line, plus a `symlink_<entry>.tmpl` for every other file or directory in the skill.
3. For Claude-only behavior (forking, a model, tool limits), build `$custom` in the Claude entry as above.

To remove a skill, delete it from both source locations _and_ add the deployed paths to `.chezmoiremove`. chezmoi does not delete a target just because its source entry disappeared, so without the `.chezmoiremove` entries the skill lingers in `$HOME` on every machine that already applied it.

Whether a skill runs inline or forked is a deliberate choice, made in the Claude entry. A forked skill (`context: fork`) runs in a fresh context that starts with no conversation history, so it suits work that a cheaper model can do from a self-contained brief and keeps its working noise out of the main conversation; the skill description tells the caller to pass such a brief. An inline skill reads the whole conversation so far, which costs more on every turn but is required when the skill has to talk to the user. The `implement` skill forks with a model that follows `agentBudget`. A forked run does not honor `disallowed-tools` (a live check of an earlier forked read-only skill still listed Write and Edit), so read-only boundaries stay in prose rather than relying on a tool lock. The `review` skill stays inline by default so the caller can choose whether a particular review merits a subagent. `github-pr` also stays inline because triage and posting confirmation must reach the user. On Codex and the other harnesses these skills are plain instructions the current agent follows; their descriptions tell a caller to use an available subagent when isolation is useful.

The `drive-implementation` skill (`/drive-implementation <plan page URL>`) drives the plan page that `plan-implementation` writes, and is deliberately thin. The plan page's `meta/guide` already owns the schema, statuses, questions, delivery, and handover, so the skill holds only how I like implementation to run: each code-changing task gets its own worktree and its own Claude agent, labelled by task so what I see reads as the plan does; every task is reviewed by a fresh subagent and fixed by its implementer, up to three rounds before the driver asks me; a reviewed task is merged onto its PR's branch and its worktree and branch removed with plain git. How the worktree and agent are made is left to whatever the harness offers (Claude Code, Herdr, and Orca each handle worktrees differently), so the skill states what the result must look like and names no tool; The skill depends on no other skill, and leaves a project's worktree conventions and CI handling to its own instructions and the plan page's guide; and the page is updated as things happen, since it is my main view of the work. It decides everything reversible itself and puts on the page only what is mine to decide, such as product behavior, scope, a PR split, or a step only a person can take, and it stops only when nothing can move without an answer. It is Claude-only: comment watches and artifact databases are Claude Code features, and the other agent kinds are no longer orchestrated natively, so the earlier `drive` (its own run page and schema) and the tracker-driven, agent-agnostic `drive-implementation` that kept me in the middle were removed. It keeps no state of its own, since the plan page is the record and a resume reconciles the page with the worktrees, agents, and PRs. The driver has to be a main-loop session, because only one of those can watch an artifact for comments, and a background subagent doesn't outlive its session, so a resumed run relaunches whatever was in flight.

The `plan-implementation` skill (`/plan-implementation <source>`) writes a detailed implementation plan on a claude.ai artifact, the plan page, for work too large or too shared for plan mode. The plan page came out of a real run, whose page was reshaped by 39 comment threads over three days, and it is the pattern for handing a plan over: the page is a generic viewer, the plan lives in the artifact's database, and a guide stored on the plan page as `meta/guide` lets an agent work it knowing only the URL. So the skill stays thin. Its `assets/` holds `plan-page.html` and `guide.md`, the guide owns the schema and the working rules, and `SKILL.md` covers only what is particular to planning: publishing the plan page, how detailed a task's plan must be, waiting, and a check by a fresh subagent before the plan is marked ready. `/drive-implementation` reads a plan page, which is why the guide already covers building. Plan mode was set aside as the container because it ends in one yes in the session and then edits in that same session, while a plan page has to outlive its session and reach people who aren't in it, and a `CLAUDE.md` rule pointing plan mode at a template would load in every session, fire on every small plan, and compete with plan mode's own instructions. The skill takes a name other than `/plan` so the built-in stays for small work. It is Claude-only for the same reason `/drive` is: comment watches and artifact databases are Claude Code features. There is no state file, since the plan page's URL is all a resume needs. When only people's answers can move the plan, the session ends its turn instead of asking through AskUserQuestion, an exception to the global rule, because a session sitting at that prompt can't be woken by an answer on the page. Herdr therefore shows such a session as idle, and an open question on the plan page is the signal. People who can edit answer questions on the page itself, which is the one place it writes: `comments: {}` lets it send Claude a comment so the watching session wakes, and `user` names who answered in the journal. Its `fixtures/` holds twelve invented plans, one for each of four shapes at three stages, for judging the layout: `executable_view <shape>-<stage>` serves one against a stand-in for the artifact runtime, inside the wrapper the Artifact tool publishes pages in, and `executable_check` holds them to the guide. The wrapper matters because the page relies on its `[hidden]` rule; without it, hidden elements such as the progress bar show. chezmoi leaves the skill's `CLAUDE.md` out of the deployed copy, so that guidance reaches sessions working on the skill and not sessions running it.

The `watch-pr` skill is the one wait primitive for a pull request: it blocks until the PR's CI finishes, someone responds, its head moves, or it merges, and exits with one JSON line, so an agent runs it in the background and is woken by its exit. It replaced watches that every agent wrote by hand; about fifty of them across one multi-agent project showed the same bugs recurring without shared code, and the script's design answers each one. A review watch keys on _unanswered_ activity (someone else's review or comment newer than my own latest) rather than a count, because agents post as my account and GitHub records each thread reply as a new review — a count-based watch fired on the agent's own replies. That same rule makes re-arming after a restart safe with no remembered baseline: a review that landed while nothing watched still reads as unanswered. A CI watch pins one commit, waits for its checks to appear, and needs two finished polls in a row so a late-starting suite is not missed; a `gh pr checks --watch | tail` watch had reported success when a network error killed it mid-run. Failed calls are retried and never read as the event.

The `worktree-layout` skill is a directory shape and the script that builds it: a plain project folder holding a primary clone, `repo/`, and optional work streams (another clone per body of work spanning several branches, such as an epic, so Herdr clusters its worktrees under their own row), with every worktree nested in its clone's `.worktrees/`. It replaced a layout of bare repos in `.bare/` directories with flat worktrees, which failed in the sandbox in two ways. A worktree couldn't write its repo's git data, because Claude Code's automatic grant for a linked worktree's main `.git` never covered a repo named `.bare`, so every worker needed a per-worktree `settings.local.json` allowance, and the one-off and review worktrees that never got one kept failing to commit. And a session in a bare repo directory, such as a driver, had no checkout, so it never loaded the repo's own skills. With ordinary clones the automatic grant works, and those sessions sit in a real checkout. What the sandbox still protects is `.git/config` and `.git/hooks`, in every clone, so `scripts/create-clone` sets the config a session would otherwise need to write (no upstream recorded on branch creation, `push.default=current`) once at clone time, and the user runs it with `!`, along with the project's hook install through its `--setup`. Leaving the sandbox through an `excludedCommands` entry or a Herdr pane was set aside: either would let any agent run it unsandboxed with any arguments, and a new clone is rare enough that a human step costs little. The script converges on re-run; it lives inside the skill rather than as a primitive of its own because nothing else uses it, and the rules and the steps that apply them read best side by side. A project opts in with one line in its own `AGENTS.md`, alongside its own facts (clone source and remote, naming convention, clone and worktree setup commands); there is no template or initializer, since that one line is all the skill needs. The line says "load X before Y" rather than "see X", because a skill loads only when an agent decides to use it. Claude reads that parent file while walking directories above a session, but Codex starts `AGENTS.md` discovery at the Git/project root, so a caller launching Codex passes the plain parent file through the supported `developer_instructions` override. How agents divide the work in such a project, and its delivery policy, stay in that project's `AGENTS.md`. A project may keep its plan in beads (`bd`), and the skill's beads section applies only then. The database sits in the plain project folder rather than any clone, so it outlives clones and can hold dependencies across work streams, and each clone reaches it through a `.beads/redirect` that `create-clone --beads` writes along with the exclude and the `beads.role` config, the last being why linking belongs in that unsandboxed step. The skill spells out the safe `bd init` because a plain one in the non-repo project folder runs `git init` there and overwrites the project's `AGENTS.md`. Codex's `workspace-write` sandbox protects a checkout's `.git` and a linked worktree's resolved Git directory, so Git metadata writes use scoped escalation; the managed `on-request` approval policy and automatic reviewer handle eligible requests without an approval override or `danger-full-access`.

Herdr's agent-state hooks are Herdr's, and these dotfiles don't manage them. `herdr integration install <agent>` writes each one (Claude's is `~/.claude/hooks/herdr-agent-state.sh`), and Herdr rewrites it on upgrade, flagging an outdated or missing one in its settings' Integrations tab. Managing Claude's copy here meant a copy-back commit after every Herdr upgrade, and until then `chezmoi apply` stopped to ask about the changed file. The `settings.json` entry that runs the hook is Herdr's as well, and the `modify_` script for that file keeps it (see Claude Code settings.json above), so a new machine gets the hook when the Claude integration is installed from Herdr. The hook's source was deleted without a `.chezmoiremove` entry, since that would delete the live file Herdr still needs.

## Global instructions and personas

Claude and Codex each read a single always-loaded instruction file (`~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`). Shared global content lives in chezmoi template partials under `.chezmoitemplates/`, so one edit updates every surface that includes it:

- **`delegation.md`** — the entry layer for running agents elsewhere: recognize a plain-language "run `<agent>` on `<task>` in a worktree or session" without a slash command, parse placement/agent/source/report-back, name artifacts for their downstream consumer, and act-on-clear/confirm-on-doubt. It names no workspace tool: an agent uses whatever its harness offers for worktrees, sessions, or subagents, and plain `git worktree` for checkouts, because a sandboxed session can't reach Herdr's or Orca's sockets. It reads a Jira task key with `jira`, settles a GitHub number as PR or issue by trying `gh pr view` before `gh issue view`, and routes GitHub PR review requests to `github-pr`, which owns their grouping and repeated queue runs. It was Herdr-only (`herdr.md`), then routed through delegation skills for Herdr and Orca, until those were retired; the parse rules were already tool-neutral. It replaced the retired `herdr-pr-review`, `herdr-start-agent`, `herdr-work-task`, `herdr-ralph-loop`, and `herdr-worktree` recipe skills.
- **`communication.md`** — how to write for a human who has an AI agent at hand: lead with the conclusion, explain references instead of pointing, favor judgment over exhaustive precision, write the current state rather than the revision history, and describe existing work neutrally. It also sets how to ask the user anything: yes/no may stay in prose, an either-or never does (it becomes multiple choice or a yes/no on the recommendation), everything else is multiple choice with the recommendation first, and several questions go in dependency order — a question whose options another answer could change waits for that answer, and the independent ones are batched (in the harness's structured question tool, or as numbered questions with lettered options). It carries the posting rule: agents post messages to people on the user's behalf only through a skill built for that kind of posting (today `github-pr`, which owns its confirmation, attribution, and posting for both reviews and the author's replies, and `jira` for Jira comments), and where no skill covers the target they draft the message for the user instead. Adding a posting skill is what grants the permission, so the rule itself needs no edit per target.

Each harness file is a thin `.tmpl` that includes the section partials that apply to it, one `{{ template ... }}` line per section:

| Harness                     | Sections included                              |
| --------------------------- | ---------------------------------------------- |
| `dot_claude/CLAUDE.md.tmpl` | `delegation` + `communication` + `claude-code` |
| `dot_codex/AGENTS.md.tmpl`  | `delegation` + `communication` + `codex`       |

`claude-code.md` holds Claude Code mechanics that would be noise elsewhere. So far that is how to drive AskUserQuestion: use it for every multiple-choice question, overriding the tool's own description, which says to save it for decisions that block the agent. That override is why the section exists: the tool description pulls the other way, and the harness-neutral rule alone did not reliably win against it. It goes further for every stop that waits on me: even a lone yes/no or a manual step goes through AskUserQuestion, because Herdr shows a session in that prompt as blocked while a prose question looks the same as a finished agent. This applied only inside Herdr at first; it is unconditional now, so the rule no longer depends on which workspace tool is running. A command I'm to run with `!` is shaped differently: an open question holds the input line, so a `Done` button meant dismissing it to type the command. The question asks only whether I'll run it, and on `I'll run it` the agent ends its turn with the command as its whole message, then checks the command's output itself when it arrives. The command used to go in a message before the question, and in 25 of 35 such questions across my transcripts the agent went from reasoning straight to the question with no message at all, so the question said "run the command above" over nothing; in three more it wrote a message without the command. The last message of a turn is reliably shown, the same lesson the `summarize-github-pr` skill taught (see Agent skills above). A `PreToolUse` hook on AskUserQuestion that refused the question until a `! ` line had been written was set aside, because the hook can't see it: a message's text is not yet in the transcript when its tool call runs. It also says that sandbox-excluded commands leave the sandbox only when run bare: a pipe or redirect silently puts them back, and xcodebuild then fails with a `permissionDenied` that doesn't mention the sandbox. Agents piped xcodebuild into `grep` out of habit, which is what kept iOS tests failing in one project. If the prose doesn't break that habit, a `PreToolUse` hook rejecting a piped or redirected excluded command is the stronger fix. Last, it tells Claude to pipe a CLI's JSON to `jq` rather than to an inline script, the one rule kept from the retired `cli-json` skill.

`codex.md` is the Codex counterpart, and so far holds one rule: a command that failed in the sandbox for a reason a retry won't change runs escalated from then on, on its first call. One Codex session ran three repository gates sandboxed, watched each fail on the network, reran it escalated, and did the same again for every round of changes, `make typos` three times over. The same session is why the `modify_` script grants Codex's sandbox the uv and npm caches Claude's sandbox may already write: without them Codex pointed each tool at a cold cache under `$TMPDIR`, which needed the network to fill.

Coordinator behavior is opt-in. Two personas remain, `coordinator` and `chief-of-staff`, with one canonical prompt each under `.chezmoitemplates/agents/personas/`. Claude Code agent files under `dot_claude/agents/` add YAML frontmatter and include the shared prompt; the same definition works as a subagent and as a primary persona through `claude --agent <name>`. Specialist work (implementing, reviewing) is done by skills rather than personas (see Agent skills), because a skill carries the same prompt to every harness without a per-harness wrapper and the coordinator can call it when it needs a specialist.

Codex uses one profile for both entry points. `dot_codex/<name>.config.toml.tmpl` deploys a launch profile selected with `codex --profile <name>`, while the `modify_` script for `config.toml` registers that same file under `[agents.<name>].config_file` so another Codex session can spawn it. Rewriting the whole `[agents]` table on each apply also drops registrations for personas that no longer exist.

The `coordinator` carries one piece of frontmatter the chief-of-staff doesn't: a `PostToolUse` hook (`dot_claude/hooks/executable_coordinator-delegation-nudge.sh`) that nudges it back toward delegating. It exists because the persona drifted into doing substantial multi-file work inline — one session ran ~20 edits across a bug fix and a full stack rebase without a single hand-off — and the prose rubric alone didn't hold. The hook reads the running transcript, counts the inline edits (`Edit`/`Write`/`NotebookEdit`) since the last delegation (an `Agent`/`Task` call, or a `Skill` call to `implement`, `review`, or `github-pr`), and the first time that run reaches three with no hand-off injects a one-time reminder to declare whether the next phase belongs with an implementor. A delegation resets the run, so a coordinator that hands off is never nagged; it fires once per run rather than on every edit past the threshold, so a legitimately-inline stretch costs at most one reminder; and it is non-blocking and fail-open (any error exits 0 with no output). Binding it through the agent's own frontmatter — rather than a global hook self-gating on the payload's `agent_type` — keeps it firing only while `coordinator` is the active agent, primary or subagent; it is a Claude Code mechanism, with no equivalent on the Codex profile. One caveat: it relies on the `PostToolUse` `additionalContext` field reaching the model, which is not guaranteed on every Claude version — if a firing never lands, switch the script's emit to the exit-code-2 path.

The `review` skill (`dot_agents/skills/review/`, `/review` when deployed) is a portable review router rather than a review engine or PR workflow. It gives one suitable reviewer already available in the harness — a caller-named reviewer first, then a native or installed reviewer, then the current agent as fallback — the implementation intent, change scope, and a shared finding model. It returns only findings introduced or meaningfully exposed by the change, normalized as `Blocker`, `Follow-up`, or (when requested) `Nit`, plus the verification performed. It makes no edits, asks the user no questions, produces no verdict or recommendation, and does not triage or post. Its description tells the caller to use an available subagent when a particular review is substantial enough to benefit from isolation; otherwise it runs inline. A delegated reviewer starts from a fresh context with the intent in the user's words and the change scope, never as a fork of the implementer's conversation. A Codex implementer once spawned its two reviews with full history (`fork_turns: "all"`); both inherited its case for a three-hour job timeout and passed it, while the repository's CI reviewer, starting fresh, found in under a minute that the job's AWS credentials expire after one hour. An inline review says so in its verification, since it isn't independent.

The `github-pr` skill (`dot_agents/skills/github-pr/`) owns every GitHub PR conversation posted on my behalf, from either side, in three modes: `review ready`, `review <n>`, and `respond <n>`. A bare number asks which mode rather than defaulting, because a number alone no longer says whether I am the reviewer or the author. It was `github-pr-review` until it gained `respond`; one skill with modes was chosen over a separate response skill plus a shared plumbing skill, because the scripts, the posting schema, and the triage-then-confirm interaction are the same on both sides, and because the posting rule grants permission per posting skill — a generic plumbing skill that could post anything would have needed its own fence.

`review ready` enumerates the current repository's open, non-draft PRs awaiting direct or team review, and background subagents review them while the session that ran `review ready` holds every triage (Claude Code and Codex both have such subagents; without them the queue says so and stops). As each review lands, it triages that PR with me, hands the confirmed review to a posting subagent, and moves on while that one posts, so I work through the queue one PR after another without waiting on a review or a post. A board, a table of the PRs and their stages, opens each PR's triage. Posting goes to a subagent so the session can move on while the poster runs its checks; it is handed the confirmed content and may change none of it, so a check that fails, such as an anchor that won't post, comes back to me rather than being fixed quietly. A review reads the PR from git without a checkout: `queue.py fetch` brings the head into a private ref (`refs/github-pr-review/<n>/head`) and the base into `origin/<base>`, and the reviewer reads `git diff <merge-base> <head>`, which is GitHub's diff, and the code around it with `git show` and `git grep` at the head. Each review used to get its own worktree on the PR's exact head branch. A checkout added little a reviewer used, since it can't run a PR's tests any more than it can read the diff without one, and it cost a lot: branch claims, a refresh and an `advance` to move a checked-out branch when the author pushed, forced worktree removal, and a branch release. All of that went, and moving to a new head is now just another fetch. Before launching, the queue looks across the batch for PRs that belong together. `ready` reports each pair's evidence (a stack, where one PR's base is another's head, a shared Jira key, shared files), and the agent judges which pairs are really one piece of work and in what order, because whether two PRs touching one file are related is judgment a script can't make. A group gets one reviewer that takes its PRs in order, the lower PR of a stack first, each with its own triage and posting, so the later reviews build on what the earlier ones read rather than relearning it; a subagent reviewer is sent each next PR as a message, which keeps its context. The queue keeps no state of its own. Whether a PR is done is read from GitHub: `ready` marks it `reviewed` when one of my recent reviews names its current head commit and is an approval, a change request, or a comment with a body (not a lone thread reply, which GitHub also records as a review). It is read per PR through GraphQL, because `gh pr list` returns only a PR's first hundred reviews. Repeated `/loop 5m /github-pr review ready` calls therefore converge: they skip a PR even while GitHub still lists a team's request, and a PR pushed since my review is new again. A review whose commit GitHub reports as null, which happens after a force-push, counts as not at the head. This replaced a state file per repository that recorded claims, holder tokens, and reviewer tabs. Most of that existed for a second mode, an interactive Claude reviewer in a Herdr or Orca tab per group, with its own launch, advance, liveness checks, and tab cleanup (which needed an auto mode exception to close tabs); that mode went with the delegation skills it ran on. Three costs were accepted: two sessions running the queue at once can review the same PR; a PR whose author answers my review without pushing stays done until review is requested again at a new head; and a PR finished without posting comes back as new in another session. The skill itself knows nothing about the coordinator; any open session with subagents can run the queue.

`review <n>` runs inline wherever it is invoked, and a queue gives each subagent the same review steps up to triage. It reads the PR and my prior review threads, invokes the generic `review` skill without Nits, asks the user to rule on each Blocker and Follow-up as Include/Exclude/Other (or a yes/no fallback), derives `REQUEST_CHANGES` only when an included Blocker remains, and asks for a final posting confirmation. Triage asks about the findings together, one question each in as few prompts as the question tool allows, and holds a finding back only when its question depends on another's ruling. The skill once said to walk through findings "individually", and in one day's sample four of the ten passes with more than one finding read that as one prompt per finding, putting 14 findings through 14 prompts; the other six batched them with no loss. On a re-review it resolves the threads of prior findings it verified as fixed, and only threads I started. It also weighs in on other reviewers' open comments, bots' included. The agent running the review judges each against the code itself, since the generic `review` skill reports only problems the change introduces, and an Agree reply gives the comment my severity, while a Dispute says with evidence why it doesn't hold. That tells the author which of several reviewers' comments matter and how much, and an Agree at Blocker requests changes like a finding of my own, which is how a bot's mild suggestion is escalated when it would break something. A finding of mine that another reviewer already raised becomes an Agree on their thread rather than a second comment. Each reply is triaged like a finding. `respond <n>` is the author's side: it runs inline with no subagents, reads every unanswered review thread, summary body, and conversation comment, drafts a reply for each grounded in evidence (a fix is cited only by a commit already on the PR), and walks the user through every draft before one confirmation. It never resolves a thread, because resolving is the reviewer's confirmation that a fix holds. It does by default re-request review from each human whose review stands at changes requested, posted after the replies, since that request otherwise blocks the merge until the reviewer happens to look again; bots are left out, because their reviews run on their own triggers. Every reply needs the user's approval, including a plain "fixed in" — a driver run that wants to close a review loop stops for the user to do it. Replying is also what lets `watch-pr --until review` re-arm, since that watch keys on activity newer than my own latest.

Both modes share two scripts and one reference. `scripts/feedback.py` prints the PR's review conversation as JSON (threads from GraphQL, which alone knows resolution state and thread ids, plus review bodies and conversation comments flagged `after_my_latest` by `watch-pr`'s rule; `respond` still lists the older ones as possibly answered, because one later reply of mine anywhere on the PR would otherwise hide every earlier summary). `scripts/post.py` posts one confirmed batch — an optional review, thread replies, one conversation comment, and resolutions — after checks that refuse the whole batch when the PR's head has moved past the batch's `head_sha`, an inline anchor is not a RIGHT-side diff line, a reply targets anything but a thread's first comment, a thread to resolve is someone else's, or a cited commit is not on the PR; `--dry-run` runs only the checks. The poster requires an attribution header but does not choose its text. The text lives in `.chezmoitemplates/posting-attribution.md`, which the skill renders with `includeTemplate ".chezmoitemplates/posting-attribution.md" . | trim` (the `trim` drops the file's trailing newline inside a code fence); a future posting skill for Jira or Slack includes the same partial so the line stays in one place. `references/posting.md` holds the batch schema and the anchoring rules. Queue discovery, head fetching, and posting used to be exposed as `list-review-requests`, `fetch-pr-head`, and `post-pr-review`; they are internal mechanics of this one discoverable workflow.

The `jira` skill (`dot_agents/skills/jira/`) is the one way agents read and change Jira, and the posting skill for Jira comments. It is instructions only, with no scripts: it works through the Atlassian MCP server, which Claude reaches through the claude.ai Atlassian connector. Scripts over Atlassian's `acli` were tried first, on the model of `github-pr` over `gh`, and set aside for two reasons. `acli` failed inside the Claude Code sandbox even with every Atlassian host allowed (later traced to its OAuth credential, which the sandbox can't read), so it would have needed its scripts excluded from the sandbox. And `acli` lacks pieces a full skill needs: it can't list transitions, look up an account for a mention, or edit custom fields. The MCP server covers all of that, takes and returns Markdown (so the shared attribution partial goes in as it is), and reports the user's own account ID in every response. What it gives up is a script to enforce the checks `github-pr`'s poster does, so the stale check (re-read the issue's `updated` before applying) and the attribution line are instructions the agent follows. The skill names tools by their base names (`getJiraIssue`, `addCommentToJiraIssue`) because the prefix differs by harness and connector. It confirms two kinds of change differently: a message to people (a comment, or a created issue's summary and description) always needs the user's confirmation, while a change to the issue itself (a transition, a field edit, a link, a new issue) needs it unless the project's instructions, or a workflow following them, authorize that specific move — which is how `drive-implementation` can make the tracker moves a project's flow calls for without stopping each time. Nothing about a particular site is in the skill: the project's own `AGENTS.md` gives its site, project keys, workflow and pre-authorized moves, and custom-field IDs, and the skill discovers and confirms anything it needs that the instructions don't give. Codex has no Atlassian MCP server configured yet; there the skill stops and says so. Wiring it is adding Atlassian's remote MCP server to Codex's config plus a one-time OAuth login per machine. The delegation partial sends a delegated task's Jira key here too. That retired the `resolve-task` primitive, which fetched Jira keys over REST with `JIRA_*` environment variables: without Jira, all it did was try GitHub's PR endpoint before the issue endpoint, which the partial now says in one sentence.

The `summarize-github-pr` and `summarize-jira-ticket` skills summarize one PR or one Jira issue for a person getting oriented on it, and any agent can reach for them; `github-pr` opens every review and respond session with the PR one, as its first message. They stay general rather than shaped for a caller, to be tuned when a real use needs more. The summary first opened triage instead, and reviewers skipped it there twice over, first as a field in `feedback.py`'s output and then as this skill: with the reviewer's findings just in, they ran the script and went straight to the first question without printing what it returned. At the start of a session the agent has nothing else to say yet, so printing the summary is its whole first message rather than one step among several, and it is where I want it anyway. Triage now opens with only a count of the findings, and the posting confirmation repeats the summary's table. Even as the whole first message, it kept getting skipped: reviewers ran the script and went straight to their next tool call, narrating a paraphrase instead, through four rewordings of the skills and a `PreToolUse` hook that refused the next tool call until the summary was shown. Yet run on its own, as `/summarize-github-pr`, the same agent printed the table without any extra guidance. The difference is the turn: an agent's last message of a turn is what it shows, while mid-turn it narrates. A `review ready` queue triages in its own session and has no such turn to give each PR, so it opens each PR's triage with its board instead, a table it composes itself, which agents do print mid-turn, and shows the summary's table in the posting confirmation. A `respond <n>` or `review <n>` session, which runs inline, relies on the skill's instruction. The PR summary is metadata only, in a fixed shape: a table of number and title (cut at 60 characters), author and URL, and when it was marked ready (or opened, if never a draft) with the PR it is stacked on (another open PR whose head is its base); then one bullet per review with its type and the number of comments it started; then the size and the base ← head branches. What the PR changes is deliberately left out, because what I want from it is a consistent way to tell PRs apart, not a description. `scripts/summary.py` prints the markdown itself, so the skill runs inline and needs no model of its own; it skips the empty reviews GitHub records for each thread reply, for the same reason `watch-pr` does. The Jira summary uses the same table, with the issue's type before its key and the assignee in place of the author; an epic follows with its status, a bar of its children by status category (█ done, ▒ in progress, ░ to do) with their counts, and its unfinished children, and any other issue with its status, parent, linked PRs (found with `gh` by key as well, since a PR is often linked only through its branch name), blockers, and subtask count. Its `scripts/summary.py` reads Jira's REST API directly rather than through the MCP server, because speed is the point: a forked agent driving the MCP tools took 40 seconds to two minutes per epic, nearly all of it model turns, and an agent running bare `acli` reads still took about 15 seconds, while the script runs every read in parallel and returns in a couple of seconds. The caller passes the site with `--site` from the project's instructions, since a work site can't be hardcoded here. The token is scoped to reading (`read:jira-work` and `read:jira-user`), so a leak can't change anything; Atlassian accepts scoped tokens only through its gateway at `api.atlassian.com`, addressed by the site's cloud ID, which the script looks up from the site's public `/_edge/tenant_info`. The email and token come from `JIRA_EMAIL` and `JIRA_API_TOKEN` in the environment, set machine-locally rather than in these dotfiles. Reading the token from 1Password at run time was tried and set aside: a sandboxed `op` can't reach the 1Password desktop app even with its config and data folders readable and its `s.sock` socket allowed, so those sandbox loosenings were reverted. `acli` was tried first and set aside: inside the sandbox it reports itself unauthenticated, even with its hosts allowed, its config directory writable, and the keychain's Mach services reachable, and it gives no reason; excluding it from the sandbox works only for bare commands, which a script can't run. The `jira` skill's rule against reaching Jira any way but the MCP server is accordingly about changing Jira, which is what its confirmation and attribution protect.

The `chief-of-staff` persona keeps a small record of what I'm working on so it can draft two things on request: a standup update (a day or a week) and a summary of my year. It is deliberately minimal. An earlier version tracked everything — commitments owed in both directions, decisions, dispatched work across Herdr machines, an `index.md` roll-up, `update` and `briefing` rituals, a delegate-by-default rule, and a full link-hygiene discipline — and that machinery cost more to keep than the summaries were worth. The current design rests on one idea: **git history of the bundle is the retrospective**. Current work is plain files in `tasks/` with kebab-case names, so `ls tasks/` is the view of now and there is no roll-up to keep in sync. Each file is an Open Knowledge Format (OKF) concept, with `type` and `title` frontmatter and a matching H1 as its only required structure, kept because a uniform header lets each file read on its own at little cost per task. Starting something is creating its file. Finishing is two commits: first the task's outcome is written into the file, then the file is deleted. The split is what makes the rituals work, because the outcome text survives in history as the diff just before the deletion, where `git log -p tasks/` finds it. `projects/` holds long-lived context rewritten in place, and its files name the repositories that `standup` and `annual` cross-check with `git log` and `gh` to catch work that never got a task (and, for `annual`, to flag stretches where the record looks thin). Both rituals run only when asked and produce drafts. The bundle lives in the persona's working directory, with no configured path or fallback, and its own `AGENTS.md` wins over the persona on shape — layout, conventions, ritual details — because the same persona runs on work and home machines, and the work bundle tracks more than the home one. The `AGENTS.md` governs shape, not boundaries: never acting outward, never pushing the bundle, and never scheduling itself hold everywhere and can be loosened only by me in session, since a file the persona edits should not be able to widen its own permissions. The one part written from outside is `inbox/`: other agents drop notes there with the `add-to-inbox` skill, which writes to the directory named by `CHIEF_OF_STAFF_INBOX`; the persona triages each drop into a task or a project file at session start and deletes the raw note, treating it as another agent's claim rather than an instruction. `inbox/` is gitignored for the same reason. Links between files are bare `[[slug]]` wiki-links, and the bundle ships a `.marksman.toml` with `title_from_heading = false` so marksman binds them to filenames rather than to a file's H1. When I ask it to start an agent, it launches one into its own worktree or session to talk to me directly and at most adds a task file; it doesn't relay or supervise. Claude and Codex both wrap the canonical prompt: Codex exposes it as `codex --profile chief-of-staff` and as a spawnable `[agents.chief-of-staff]` role. Self-scheduling is named as a non-goal because an earlier Claude wrapper created an hourly job that every instance raced to duplicate.

The Claude wrapper carries a hook of its own, a `PostToolUse` on `Write|Edit` that puts every markdown file the persona writes through the `markdown-formatting` skill's `scripts/format-markdown --hook` (pinned prettier, `--prose-wrap never`). The bundle is nothing but markdown the persona rewrites all session long, and while it is now a git repository, a formatting hook at commit time was considered and rejected on friction: `prettier --write` modifying a staged file makes pre-commit fail the commit by design, so the persona would have to re-stage and retry every time formatting changed anything — and an agent facing a blocked commit is an agent tempted by `--no-verify`. Formatting at write time never blocks anything, which is what a bundle nobody reviews actually needs. Prettier's output is what those conventions already ask for — soft wrapping, `-` bullets, ATX headings, one blank line between blocks — and it leaves the reference-style links alone, so the hook mechanizes the persona's own style rather than imposing a second one. That skill's README argues against installing this hook globally, because a global formatter silently reflows other people's repositories that hard-wrap by convention, and says to opt in per project instead; binding it to the persona answers the same objection without a per-project step, since the only markdown this persona writes is its own bundle. There is no Codex counterpart. Codex hooks exist and a profile can carry them inline, but its `apply_patch` payload puts patch text in `tool_input.command` rather than a `file_path`, so the shared script would have to parse an envelope Codex owns and does not document — and would go back to silently doing nothing the day that envelope changed, because `--hook` swallows its own failures by design. An `apply_patch` matcher would also still miss markdown written through a shell heredoc. So the prompt keeps telling the persona to write the markdown correctly rather than pointing at a formatter: on Codex that discipline is still the only thing there is, and on Claude the hook is a backstop the persona is better off not counting on.

The bundle is live state the persona rewrites constantly, so chezmoi does not manage or seed it. On first use in a chosen working directory, the persona runs `git init` and creates the `.marksman.toml` its link scheme depends on and a `.gitignore` covering `inbox/` and `.DS_Store`; `tasks/`, `projects/`, and whatever else the bundle's `AGENTS.md` defines arise with their first entries, and `inbox/` arises when an agent first drops a note (the `add-to-inbox` script creates it if missing). Codex's ordinary `workspace-write` sandbox already grants access to that working directory, so the profile needs no extra writable root. Removing the former `dot_local/state/chief-of-staff/create_index.md` source deliberately does not add `~/.local/state/chief-of-staff/` to `.chezmoiremove`: existing live state is user data and must remain untouched. `.chezmoiremove` still deletes the persona's original `~/.claude/cos/` seed so that retired format does not linger on machines that applied it.

Model and concurrency choices come from the machine-local `agentBudget` datum. `.chezmoi.toml.tmpl` asks for `conservative` or `generous` during `chezmoi init` and defaults to `conservative`; consuming templates also fall back to conservative when the datum is absent or unrecognized. This keeps existing machines safe until their chezmoi config is regenerated or gains `agentBudget` under `[data]`. It sets the personas' models, and the model of the forked `implement` skill on Claude.

| Persona or skill  | Claude conservative / generous | Codex conservative / generous |
| ----------------- | ------------------------------ | ----------------------------- |
| Coordinator       | Sonnet / Opus                  | Terra medium / Sol high       |
| Chief of staff    | Sonnet / Opus                  | Terra medium / Sol high       |
| `implement` skill | Sonnet / Opus                  | the session's own model       |

Codex skills run on whatever model the current session uses; only the two personas have Codex profiles.

Codex caps spawned-agent threads at two for conservative machines and four for generous machines. These choices apply only to persona profiles and the subagent cap; the ordinary top-level Codex model remains the independently configured default.

The global harnesses do not include a persona. They keep delegation and communication conventions available in ordinary sessions without forcing every session to coordinate. Codex's skills need no wiring because it reads `~/.agents/skills/` natively (see the Agent skills table above). A harness that needs its own global content adds it before or after the includes.

The harness files are `.tmpl`, not `.md`, so the `prettier` pre-commit hook (which runs with `proseWrap: never`) leaves their one-include-per-line layout alone; that layout matters because the render joins the sections with the blank lines between them. The section partials themselves are prose `.md` and stay prettier-managed. This is why there is no `agent-behaviors.md` wrapper partial: a `.md` composition file would get its include lines collapsed onto one line by prettier.

## Key tools configured

- **Shell**: zsh with starship prompt, zsh-autosuggestions, zsh-syntax-highlighting, direnv
- **Terminal**: Ghostty (ligatures disabled)
- **Prompt**: Starship — configured without Nerd Font glyphs, kubernetes module enabled
- **Git**: pull.rebase=true, rebase.updateRefs=true, rebase.autoSquash=true
- **AWS profile switching**: `aws-profile-login` / `aws-profile-logout` are zsh functions in `dot_config/kris-steinhoff/zshrc`, not scripts. They must be functions because they set `AWS_PROFILE` in the interactive shell — a standalone script would only mutate its own subprocess. `aws-profile-login` triggers SSO or static login if the current credentials are invalid, adding `--use-device-code` when `$SSH_CONNECTION` is set (a remote session with no local browser).
- **Scripts**:
  - `dot_local/bin/executable_ai-usage` — shows usage for Claude, ChatGPT, and OpenRouter. A `uv run --script` Python tool that reads Claude Code's OAuth credential (`~/.claude/.credentials.json`, or the macOS Keychain) and Codex's ChatGPT credential (`~/.codex/auth.json`) and queries their respective usage endpoints. It adapts to the windows each account reports; `--service` (repeatable) limits the view to the named providers. OpenRouter is prepaid credits rather than a subscription, so its panel shows the account's balance, a bar per budget enforced on the key, and the key's spend today, this week, and this month. Its keys come from the environment, set machine-locally like the Jira token: `OPENROUTER_API_KEY` for the key's spend and budgets, and `OPENROUTER_MANAGEMENT_KEY` for the balance, because OpenRouter's balance endpoint accepts only a management key, which can also create and delete keys. Either one alone is enough, and a machine with neither hides the panel. Because sign-in can differ between callers when it comes from the environment, a missing credential is never written to the shared cache, so a caller without the keys can't hide OpenRouter from one that has them. On a terminal it refreshes live in place until Ctrl-C, with Ctrl-R forcing a refresh. `--once` prints a single snapshot and exits, `--json` emits raw payloads keyed by provider, and `--json windows` emits every service's windows (key, percent used, length, reset time) and status in one shape for a script that compares them, without failing on a service it can't read. Every mode reads through a shared per-service cache in `~/.local/state/ai-usage/`, so any number of callers (a status line, several live views) can run as often as they like without drawing 429s: a caller fetches only when the last attempt is older than its `--interval` (default 300), and a file lock makes concurrent stale callers wait for one fetch rather than each making their own. Failed attempts are cached too, so callers back off from an error together; a 429's Retry-After binds even Ctrl-R, since forcing through it only draws another 429. The cache holds the payload and the Claude plan name, never tokens. Run inside the Claude sandbox, it needs to reach `api.anthropic.com`, `chatgpt.com`, and `openrouter.ai` and to write that cache; `settings.json` grants all of them.
