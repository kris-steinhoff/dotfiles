# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a personal dotfiles repository managed with [chezmoi](https://chezmoi.io/). This repo is the chezmoi source directory — files use chezmoi naming conventions (`dot_` prefix for dotfiles, `executable_` prefix for scripts) and are applied to `$HOME` by chezmoi.

## Signaling the user

When the `signal-user` skill is available, use it each time you stop: ✋🏽 before asking the user something, ✓ when there is a commit or other result for them to look at, and `…` when you end your turn waiting on something that will wake you. Outside Herdr it does nothing, so there is no need to check first.

## Bootstrap

To set up a new machine:

```bash
chezmoi init kris-steinhoff/dotfiles
chezmoi apply
```

`chezmoi init` clones this repo to `~/.local/share/chezmoi`. `chezmoi apply` copies managed files to `$HOME` and runs `run_once_bootstrap.sh`, which:

1. Ensures `~/.zshrc`, `~/.config/git/config`, and `~/.vimrc` each source/include the shared config files under `~/.config/kris-steinhoff/`
2. Runs `brew bundle install` from `~/.config/homebrew/Brewfile` if Homebrew is available
3. Runs `nvim --headless "+Lazy! restore" +qa` to install Neovim plugins at the commits pinned in `lazy-lock.json`

## Neovim plugin pinning

`dot_config/nvim/lazy-lock.json` is checked in. lazy.nvim installs plugins at the commits recorded there, which guards against supply-chain compromise of upstream repos. The bootstrap step above installs from the lockfile rather than letting plugins float to HEAD.

When updating plugins:

1. Run `:Lazy update` inside nvim.
2. Review the diff in `~/.config/nvim/lazy-lock.json`.
3. `chezmoi re-add ~/.config/nvim/lazy-lock.json` to pull the new commits into the source dir, then commit.

Without step 3, the next `chezmoi apply` will revert the lockfile to whatever's checked in.

## Claude Code settings.json key ordering

Claude Code rewrites `~/.claude/settings.json` with its own key ordering whenever it changes something internally (e.g. saving a permission), even when the values are unchanged. Because `chezmoi apply` refuses to overwrite a target that has changed since it last wrote it, this reordering alone trips that guard and produces a warning that's usually just noise.

Both sides are kept sorted the same way so ordering never causes a spurious diff:

- `dot_claude/private_settings.json` (the checked-in source) is sorted by the local `sort-claude-settings-json` pre-commit hook (`jq -S`).
- `~/.claude/settings.json` (the live file) is kept sorted by a `ConfigChange` hook, `dot_claude/hooks/executable_sort-settings-json.sh`, which re-sorts it with the same `jq -S` after every change.

A `chezmoi apply` warning on this file should now only mean a real value changed, not just key order.

## Codex config.toml machine-local state

Codex rewrites `~/.codex/config.toml` at runtime and injects machine-local state that must not be version-controlled: `[projects.*]` trust levels (per-machine checkout paths), `[tui.*]` UI counters, and `[hooks.*]` trusted hook hashes. A plain template would clobber that state on every apply and force re-trusting projects and hooks.

So the source is a chezmoi `modify_` script, `dot_codex/modify_private_config.toml.tmpl`, rather than a static template. A `modify_` script receives the current target on stdin and its stdout becomes the new file. The script is a `uv`-run Python program that parses the live file with `tomlkit`, sets only the settings we manage (`model`, `project_doc_fallback_filenames`, `approval_policy`, `approvals_reviewer`, `[features]`, `[agents]` — the last templated on `agentBudget`), and dumps the document back. Because `tomlkit` preserves the layout of everything it does not touch, Codex's machine-local tables round-trip verbatim, applies are idempotent (a clean machine shows no diff), and nothing is silently dropped whatever new keys Codex may add. This needs `uv` present at apply time (it is in the Brewfile); the earlier `awk`-based version avoided that dependency but classified sections by regex and could drop unknown top-level bare keys.

The shebang pulls `tomlkit` via `uv run --with tomlkit`, not PEP 723 inline metadata (`--script`). This matters because `uv run --script` keys its ephemeral venv on the script's file path, and chezmoi runs a `modify_` script from a fresh temp path on every apply — so that env never hit the cache and uv reinstalled the dep (printing `Installed 1 package`) on every `chezmoi apply`. A `--with` env is keyed on its requirements instead, so it survives the changing paths and uv only rebuilds (and reports) it on a cold cache or a dep bump. The tradeoff is that this script alone differs from the PEP 723 pattern `ai-usage` uses.

The filename attribute order is `modify_private_` (type prefix before the `private_` permission attribute); `private_modify_` is not recognized and chezmoi treats the leftover `modify_` as a literal filename.

## Config architecture

Shared configs live under `dot_config/kris-steinhoff/` (deployed to `~/.config/kris-steinhoff/`) and are _included_ by the machine-local config files (not replaced). This lets local overrides coexist with the shared baseline:

| Shared file                          | Included by            |
| ------------------------------------ | ---------------------- |
| `~/.config/kris-steinhoff/zshrc`     | `~/.zshrc`             |
| `~/.config/kris-steinhoff/gitconfig` | `~/.config/git/config` |
| `~/.config/kris-steinhoff/vimrc`     | `~/.vimrc`             |

The `run_once_bootstrap.sh` script uses `ensure_config` to add the include line automatically, prompting the user when a file already exists but doesn't include the shared config.

## Agent skills

A skill is authored once and shared across every agent surface, so its content is edited in exactly one place. The canonical copy is a real directory under `dot_agents/skills/`, which deploys to `~/.agents/skills/`.

Each skill directory follows the [agentskills.io](https://agentskills.io/specification) format: a required `SKILL.md` with `name`/`description` frontmatter, plus optional `scripts/` (executable code), `references/` (documentation loaded on demand), and `assets/` (templates, static resources) subdirectories.

That location is the cross-agent convention, not an arbitrary pick. Codex and OpenCode both read `~/.agents/skills/` natively, so they use the canonical copy as it is. Claude Code and Gemini look elsewhere, so each gets its own entry for the skill that is rendered from the canonical one.

The canonical file is `SKILL.md.tmpl`, a template, because the harnesses do not agree on frontmatter. Claude Code understands fields such as `context: fork`, `model`, and `disallowed-tools` that other harnesses ignore or choke on, and the right values (the model, for one) depend on the machine's `agentBudget`. So the canonical frontmatter holds only `name` and `description`, and ends with a hook that splices in whatever extra lines the including template supplies:

```
{{- with get . "custom" }}
{{ . }}
{{- end }}
```

Each surface then sees only the fields it should:

| Surface         | Source path                                                            | Frontmatter                          |
| --------------- | ---------------------------------------------------------------------- | ------------------------------------ |
| Canonical       | `dot_agents/skills/<name>/SKILL.md.tmpl`                               | `name`, `description`, and no extras |
| Codex, OpenCode | none, they read `~/.agents/skills/` natively                           | same as canonical                    |
| Claude Code     | `dot_claude/skills/<name>/SKILL.md.tmpl`                               | canonical plus Claude-only fields    |
| Gemini          | `dot_gemini/config/plugins/kris-steinhoff/skills/<name>/SKILL.md.tmpl` | same as canonical                    |

A Gemini entry, and a Claude entry with nothing extra, is one line that renders the canonical template:

```
{{- includeTemplate "dot_agents/skills/<name>/SKILL.md.tmpl" . -}}
```

A Claude entry with extras builds the lines first and merges them into the context, which is how the model follows `agentBudget`:

```
{{- $model := ternary "opus" "sonnet" (eq (get . "agentBudget") "generous") -}}
{{- $custom := printf `context: fork
agent: general-purpose
background: false
model: %s` $model -}}
{{- includeTemplate "dot_agents/skills/<name>/SKILL.md.tmpl" (merge (dict "custom" $custom) .) -}}
```

`includeTemplate` takes its path from the source directory root, like `include`. Claude-only fields never go into the canonical frontmatter; they live in the Claude entry.

Everything in a skill directory other than `SKILL.md` (`scripts/`, `references/`, `assets/`, or other loose files) is not templated. Each Claude and Gemini entry directory gets a `symlink_<entry>.tmpl` per such file or directory, whose entire body is the link target:

```
{{ .chezmoi.homeDir }}/.agents/skills/<name>/<entry>
```

The executable bit lives only on the canonical copy (the `executable_` prefix is dropped from the link name), so a script is never duplicated. A `symlink_` entry sitting where chezmoi used to apply a whole-skill symlink converts to a real directory on the next apply, so no `.chezmoiremove` entry is needed for that move.

The Gemini surface is a plugin, not a plain skills directory. `dot_gemini/config/plugins/kris-steinhoff/plugin.json` declares it, and the skill directories live in that plugin's `skills/` subdirectory.

To add a skill:

1. Write `dot_agents/skills/<name>/SKILL.md.tmpl` with the hook above, using `chezmoi add` for any scripts (it applies the `executable_` prefix to nested scripts such as `scripts/` helpers, which a manual copy would miss). This alone is enough for Codex and OpenCode.
2. Create `dot_claude/skills/<name>/SKILL.md.tmpl` and the Gemini equivalent with the `includeTemplate` line, plus a `symlink_<entry>.tmpl` in each for every other file or directory in the skill.
3. For Claude-only behavior (forking, a model, tool limits), build `$custom` in the Claude entry as above.

To remove a skill, delete it from all three source locations _and_ add the deployed paths to `.chezmoiremove`. chezmoi does not delete a target just because its source entry disappeared, so without the `.chezmoiremove` entries the skill lingers in `$HOME` on every machine that already applied it.

Whether a skill runs inline or forked is a deliberate choice, made in the Claude entry. A forked skill (`context: fork`) runs in a fresh context that starts with no conversation history, so it suits work that a cheaper model can do from a self-contained brief and keeps its working noise out of the main conversation; the skill description tells the caller to pass such a brief. An inline skill reads the whole conversation so far, which costs more on every turn but is required when the skill has to talk to the user. The `implement` skill forks with a model that follows `agentBudget`; `investigate` stays on `sonnet` regardless of the budget. A forked run does not honor `disallowed-tools` (a live check of the `investigate` still listed Write and Edit), so read-only boundaries stay in prose rather than relying on a tool lock. The `review` skill stays inline by default so the caller can choose whether a particular review merits a subagent. `github-pr` also stays inline because triage and posting confirmation must reach the user. On Codex and the other harnesses these skills are plain instructions the current agent follows; their descriptions tell a caller to use an available subagent when isolation is useful.

The `watch-pr` skill is the one wait primitive for a pull request: it blocks until the PR's CI finishes, someone responds, its head moves, or it merges, and exits with one JSON line, so an agent runs it in the background and is woken by its exit. It replaced watches that every agent wrote by hand; about fifty of them across one multi-agent project showed the same bugs recurring without shared code, and the script's design answers each one. A review watch keys on _unanswered_ activity (someone else's review or comment newer than my own latest) rather than a count, because agents post as my account and GitHub records each thread reply as a new review — a count-based watch fired on the agent's own replies. That same rule makes re-arming after a restart safe with no remembered baseline: a review that landed while nothing watched still reads as unanswered. A CI watch pins one commit, waits for its checks to appear, and needs two finished polls in a row so a late-starting suite is not missed; a `gh pr checks --watch | tail` watch had reported success when a network error killed it mid-run. Failed calls are retried and never read as the event.

The `cleanup-worktrees` skill (`/cleanup-worktrees`) is the one teardown for worktrees: it removes every worktree it can without losing work or interrupting anything, closing its Herdr workspace with it, and deletes the branch with `git branch -d`. Its safety rule rests on the branch outliving the checkout: a clean worktree's commits stay on its branch, and `-d` refuses a branch that isn't fully merged, so unpushed or unmerged work never blocks removal and the unmerged branch is quietly left behind. That is why it doesn't share `remove-worktree`'s unpushed-commits gate, which made `drive-implementation` pass `--force` for every unit whose branch had no upstream; `drive-implementation` now calls this skill for each landed unit and finished experiment, and `remove-worktree` stays as the lower-level single-worktree primitive `github-pr` uses, since review branches need `release`'s on-the-PR check rather than `-d`. It always keeps the checkout of the repo's `HEAD` or origin's default branch, because in a bare-backed repo directory the default branch is an ordinary worktree and `-d` would delete the branch the bare repo's `HEAD` names. A live agent holds its worktree until it says it is done: the script reports the agents, the skill asks each idle one a fixed yes-or-no question, and a second run with `--done-agent` removes the worktree, which ends the agent by closing its workspace (Herdr has no stop command). The asking lives in the skill rather than the script because reading an agent's free-text answer is judgment, and the second run re-checks everything so an agent that started working in between still holds its worktree.

The `choose-agent` skill picks which agent kind and model to launch, so a dispatcher spreads work across subscriptions and steers away from one that is nearly spent. `drive-implementation` runs it for each agent's first launch; it replaced a fixed 60/40 coin flip between Codex and Claude. Which agents a machine has is declared, not discovered, in an unmanaged `~/.config/choose-agent/candidates.toml`, because usage data can't see an agent that has no quota: a local model never appears in `ai-usage`. Each candidate names a launcher kind, an optional model, its quota (`claude`, `chatgpt`, or `none`), and a base weight; with no file the candidates are Claude and Codex at 40/60, and any whose CLI is off PATH drops out. Usage only adjusts metered candidates. Each relevant window scores the share of capacity left divided by the share of time left before it resets, so a week about to reset half unused counts high (that capacity is otherwise lost) and a nearly spent session counts low, and a window at 90% rules its candidate out. A candidate signed out of its quota drops out, which is how a machine with only one subscription needs no configuration. A failed usage read leaves the base weights alone, so telemetry never blocks a launch. The pick is weighted-random, not the top score, because a driver starts units in bursts against one cached snapshot and the top score would send the whole burst to one place. Preferences stay out of the script: the caller reads them from the user, the unit, and the repository's instructions and passes `--only`, `--exclude`, or `--prefer`, and a needs-judgment exit (nothing available, or everything at its limit) goes to the user rather than being relaxed. The kind decides how a launched agent reports back, so `launch-agent-in-pane` writes those instructions per kind: a Claude worker reports by `SendMessage` when the caller passes `--report-to-session`, and every other kind reports with a `[<agent name>]`-tagged `herdr agent prompt` into the caller's pane, the tag being what tells the caller it is not the user typing. The usage figures come from `ai-usage --json windows`, which needs the Claude sandbox to reach `api.anthropic.com` and `chatgpt.com` and to write the shared cache in `~/.local/state/ai-usage/`; `settings.json` grants all three.

The `signal-user` skill shows why an agent stopped in the Herdr sidebar: ✋🏽 needs my answer, ✓ has a specific result to inspect, and `…` is waiting on work that will wake it. Signaling is opt-in: `drive-implementation`, `github-pr`, and the `chief-of-staff` persona call for it at their stop points, while other agents use it only when I ask. The chief of staff raises ✋🏽 and ✓ but never `…`, because it never waits on the work it dispatches. Signals are workspace metadata owned by the raising pane, so they do not rename agents; the Herdr plugin clears ✋🏽 and ✓ when that pane resumes, while wrapped waits clear their own `…` on exit. The skill's [design reference](dot_agents/skills/signal-user/references/design.md) holds the lifecycle, precedence, Codex fallback, and integration details.

The `worktree-layout` skill is a directory shape and the script that builds it: a project directory backed by a bare repo in `.bare/` with every checkout a flat worktree in it, plus optional work streams (a second bare repo for a body of work spanning several branches, such as an epic, so Herdr clusters its worktrees under their own row). Its `scripts/create-bare-repo` makes a repo directory and converges on re-run like the dispatch primitives; it lives inside the skill rather than as a primitive of its own because nothing else uses it, and the rules and the steps that apply them read best side by side. A project opts in with one line in its own `AGENTS.md`, alongside its own facts (clone source and remote, naming convention, worktree setup commands); there is no template or initializer, since that one line is all the skill needs. The line says "load X before Y" rather than "see X", because a skill loads only when an agent decides to use it, while `AGENTS.md` is read from every directory above a session. How agents divide the work in such a project, and its delivery policy, stay in that project's `AGENTS.md` for now. The skill describes the Claude Code sandbox grant a worktree needs to write its repo's `.bare/`, but nothing here writes that grant, because widening the sandbox stays the user's decision.

One skill is not authored here. Herdr ships its own skill text and prints it with `herdr --skill`, so `dot_agents/skills/herdr/herdr.md` is that output vendored verbatim and `SKILL.md.tmpl` is a chezmoi template that inlines it and carries our own additions below the include. Refreshing upstream is `herdr --skill > dot_agents/skills/herdr/herdr.md`, a whole-file overwrite that cannot clobber anything we wrote, and whose `git diff` is exactly what upstream changed. Keep `herdr.md` unedited for that reason: a correction that belongs upstream goes upstream, not into the vendored copy.

Templating is what makes the split free; the Claude and Gemini entries for `herdr` are the plain `includeTemplate` line, and the nested `include` resolves from the same source root. Because chezmoi renders before deploying, every surface gets one self-contained `SKILL.md` and no agent has to be told to go read a second file — which rules out the quiet failure where it skips the read and drives Herdr without the `HERDR_ENV` gate or the safety rules. A prose pointer would have been needed instead: skills have no `@file` include (that inlining is a CLAUDE.md memory feature), and three of the four surfaces here are not Claude anyway.

Two mechanics to know. `include` resolves relative to the source directory root, not to the template's own directory, so the path inside `SKILL.md.tmpl` is the full `dot_agents/skills/herdr/herdr.md` even though the two files sit side by side; `./herdr.md` silently looks in the wrong place. And `herdr.md` is a template input rather than a file of its own, so `.chezmoiignore` excludes its target path — without that, each machine also gets a redundant second copy of the text in `~/.agents/skills/herdr/`.

The rendered `SKILL.md` therefore begins with upstream's frontmatter, which is deliberate: nothing about the skill's registration is hand-maintained, and a refresh keeps the `name` and `description` current for free. The cost is that local additions cannot change when the skill fires. If one ever needs to, strip the leading frontmatter out of the include and write our own above it — at which point that description becomes ours to maintain by hand.

The space below the include holds one addition so far: `scripts/herdr-ssh`, a fallback for reaching another machine when `herdr --machine <label> <cmd>` cannot forward. Forwarding binds a local unix socket in `$TMPDIR`, which a sandboxed session is not permitted to do, so the command dies with `PermissionDenied` (os error 1) before it reaches the remote. The script runs Herdr natively on the far side over plain SSH instead: it resolves a saved machine through `herdr machine list --json` and then `ssh -G` (so ssh_config Includes and aliases apply), connects to the literal loopback IP because `localhost` resolution fails in that environment with error -65563, and shell-quotes the remote command because ssh hands it to the remote shell to re-split — the reason an unquoted multi-word `--label` or seed prompt arrives as separate arguments. `--machine` stays the default and the skill says so; this is what to reach for when it is unavailable.

Authentication failures exit as needs-judgment rather than as errors to retry, and both the script and the skill say to stop and tell the user rather than troubleshoot. The key lives in a 1Password SSH agent, so a failure almost always means its macOS unlock prompt was dismissed or went unnoticed — a human-attention problem that an agent can only make worse by working around it, and that the user cannot fix unless someone tells them that is what happened.

One judgment call worth keeping: host-key verification is relaxed only for loopback targets. A container's key changes with every rebuild and nothing can impersonate 127.0.0.1, so skipping it there costs nothing — but one of the saved ssh_config hosts is a routable public IP, where the same shortcut would trade away real protection, so those keep normal `known_hosts` checking unless `--host-key-checks off` is passed explicitly.

## Global instructions and personas

Claude, Gemini, and Codex each read a single always-loaded instruction file (`~/.claude/CLAUDE.md`, `~/.gemini/GEMINI.md`, and `~/.codex/AGENTS.md`). Shared global content lives in chezmoi template partials under `.chezmoitemplates/`, so one edit updates every surface that includes it:

- **`herdr.md`** — the entry layer for Herdr: recognize a plain-language "run `<agent>` on `<task>` in a worktree/pane/tab" without a slash command, parse placement/agent/source/report-back, name artifacts for their downstream consumer, and act-on-clear/confirm-on-doubt. It routes ordinary mechanics through `herdr`, `create-worktree`, and `launch-agent-in-pane`, reads a Jira task key with `jira`, and settles a GitHub number as PR or issue by trying `gh pr view` before `gh issue view`, while GitHub PR review requests route to `github-pr`, which owns their exact-head worktrees and repeated queue dispatch. It also covers launching a persona into a pane (`launch-agent-in-pane --persona`, which only the coordinator and chief-of-staff use). This replaced the retired `herdr-pr-review`, `herdr-start-agent`, `herdr-work-task`, `herdr-ralph-loop`, and `herdr-worktree` recipe skills. It is gated on `HERDR_ENV=1`, so it stays inert where Herdr is not running.
- **`communication.md`** — how to write for a human who has an AI agent at hand: lead with the conclusion, explain references instead of pointing, favor judgment over exhaustive precision, write the current state rather than the revision history, and describe existing work neutrally. It also sets how to ask the user anything: yes/no may stay in prose, an either-or never does (it becomes multiple choice or a yes/no on the recommendation), everything else is multiple choice with the recommendation first, and several questions go in dependency order — a question whose options another answer could change waits for that answer, and the independent ones are batched (in the harness's structured question tool, or as numbered questions with lettered options). It carries the posting rule: agents post messages to people on the user's behalf only through a skill built for that kind of posting (today `github-pr`, which owns its confirmation, attribution, and posting for both reviews and the author's replies, and `jira` for Jira comments), and where no skill covers the target they draft the message for the user instead. Adding a posting skill is what grants the permission, so the rule itself needs no edit per target.

Each harness file is a thin `.tmpl` that includes the section partials that apply to it, one `{{ template ... }}` line per section:

| Harness                     | Sections included                         |
| --------------------------- | ----------------------------------------- |
| `dot_claude/CLAUDE.md.tmpl` | `herdr` + `communication` + `claude-code` |
| `dot_gemini/GEMINI.md.tmpl` | `herdr` + `communication`                 |
| `dot_codex/AGENTS.md.tmpl`  | `herdr` + `communication`                 |

`claude-code.md` holds Claude Code mechanics that would be noise elsewhere. So far that is how to drive AskUserQuestion: use it for every multiple-choice question, overriding the tool's own description, which says to save it for decisions that block the agent. That override is why the section exists: the tool description pulls the other way, and the harness-neutral rule alone did not reliably win against it. It also says that sandbox-excluded commands leave the sandbox only when run bare: a pipe or redirect silently puts them back, and xcodebuild then fails with a `permissionDenied` that doesn't mention the sandbox. Agents piped xcodebuild into `grep` out of habit, which is what kept iOS tests failing in one project. If the prose doesn't break that habit, a `PreToolUse` hook rejecting a piped or redirected excluded command is the stronger fix.

Coordinator behavior is opt-in. Two personas remain, `coordinator` and `chief-of-staff`, with one canonical prompt each under `.chezmoitemplates/agents/personas/`. Claude Code agent files under `dot_claude/agents/` add YAML frontmatter and include the shared prompt; the same definition works as a subagent and as a primary persona through `claude --agent <name>`. Specialist work (implementing, investigating, reviewing) is done by skills rather than personas (see Agent skills), because a skill carries the same prompt to every harness without a per-harness wrapper and the coordinator can call it when it needs a specialist.

Codex uses one profile for both entry points. `dot_codex/<name>.config.toml.tmpl` deploys a launch profile selected with `codex --profile <name>`, while the `modify_` script for `config.toml` registers that same file under `[agents.<name>].config_file` so another Codex session can spawn it. Rewriting the whole `[agents]` table on each apply also drops registrations for personas that no longer exist.

The `coordinator` carries one piece of frontmatter the chief-of-staff doesn't: a `PostToolUse` hook (`dot_claude/hooks/executable_coordinator-delegation-nudge.sh`) that nudges it back toward delegating. It exists because the persona drifted into doing substantial multi-file work inline — one session ran ~20 edits across a bug fix and a full stack rebase without a single hand-off — and the prose rubric alone didn't hold. The hook reads the running transcript, counts the inline edits (`Edit`/`Write`/`NotebookEdit`) since the last delegation (an `Agent`/`Task` call, or a `Skill` call to `implement`, `investigate`, `review`, or `github-pr`), and the first time that run reaches three with no hand-off injects a one-time reminder to declare whether the next phase belongs with an implementor. A delegation resets the run, so a coordinator that hands off is never nagged; it fires once per run rather than on every edit past the threshold, so a legitimately-inline stretch costs at most one reminder; and it is non-blocking and fail-open (any error exits 0 with no output). Binding it through the agent's own frontmatter — rather than a global hook self-gating on the payload's `agent_type` — keeps it firing only while `coordinator` is the active agent, primary or subagent; it is a Claude Code mechanism, with no equivalent on the Codex profile. One caveat: it relies on the `PostToolUse` `additionalContext` field reaching the model, which is not guaranteed on every Claude version — if a firing never lands, switch the script's emit to the exit-code-2 path.

The `review` skill (`dot_agents/skills/review/`, `/review` when deployed) is a portable review router rather than a review engine or PR workflow. It gives one suitable reviewer already available in the harness — a caller-named reviewer first, then a native or installed reviewer, then the current agent as fallback — the implementation intent, change scope, and a shared finding model. It returns only findings introduced or meaningfully exposed by the change, normalized as `Blocker`, `Follow-up`, or (when requested) `Nit`, plus the verification performed. It makes no edits, asks the user no questions, produces no verdict or recommendation, and does not triage or post. Its description tells the caller to use an available subagent when a particular review is substantial enough to benefit from isolation; otherwise it runs inline.

The `github-pr` skill (`dot_agents/skills/github-pr/`) owns every GitHub PR conversation posted on my behalf, from either side, in three modes: `review ready`, `review <n>`, and `respond <n>`. A bare number asks which mode rather than defaulting, because a number alone no longer says whether I am the reviewer or the author. It was `github-pr-review` until it gained `respond`; one skill with modes was chosen over a separate response skill plus a shared plumbing skill, because the scripts, the posting schema, and the triage-then-confirm interaction are the same on both sides, and because the posting rule grants permission per posting skill — a generic plumbing skill that could post anything would have needed its own fence.

`review ready` enumerates the current repository's open, non-draft PRs awaiting direct or team review, prepares each exact GitHub head branch, and launches one interactive Claude reviewer in a Herdr worktree. Its internal dispatch helper records the PR number, head SHA, and pass status inside the existing `.herdr-dispatch.json` provenance marker, so repeated `/loop 5m /github-pr review ready` calls skip active and completed heads, defer a changed head while review is active, and refresh only a completed clean worktree. The marker key (`github_pr_review`) and the helper's private refs (`refs/github-pr-review/<n>/…`) kept their names through the rename, so passes in flight on existing machines still converge. Each pass also cleans up: every completed review worktree is removed with `remove-worktree --force` and its exact-head branch released, whatever the review's outcome. Keeping a worktree until approval would leave one open for every PR awaiting the author's fixes, and nothing needs it: a re-review reads my earlier findings from GitHub rather than the old checkout, so when the author re-requests review the next pass builds a fresh worktree. The force is deliberate, because the finished reviewer idles in its pane and the branch has no upstream, so the generic gate would always refuse; the helper's own `cleanup` check covers what that gate protects (a clean tree at the reviewed head), and `release` deletes the branch only when its commits are on the PR's fetched head. This is the one standing exception to the Herdr rule that teardown happens only when asked, made because finished reviews should not pile up as worktrees. The skill itself knows nothing about the coordinator; any open Claude session with Herdr can run the loop. An unrelated exact-name branch is reported and left untouched rather than suffixed, because preserving the branch identity is what lets Claude's UI link the checkout to its PR.

`review <n>` dispatches the PR when invoked outside its review worktree, then becomes the interactive half inside that checkout. It reads the PR and my prior review threads, invokes the generic `review` skill without Nits, walks the user through each Blocker and Follow-up as Include/Exclude/Other (or a yes/no fallback), derives `REQUEST_CHANGES` only when an included Blocker remains, and asks for a final posting confirmation. On a re-review it resolves the threads of prior findings it verified as fixed, and only threads I started. `respond <n>` is the author's side: it runs inline with no dispatch, reads every unanswered review thread, summary body, and conversation comment, drafts a reply for each grounded in evidence (a fix is cited only by a commit already on the PR), and walks the user through every draft before one confirmation. It never resolves a thread, because resolving is the reviewer's confirmation that a fix holds. Every reply needs the user's approval, including a plain "fixed in" — a driver run that wants to close a review loop stops for the user to do it. Replying is also what lets `watch-pr --until review` re-arm, since that watch keys on activity newer than my own latest.

Both modes share two scripts and one reference. `scripts/feedback.py` prints the PR's review conversation as JSON (threads from GraphQL, which alone knows resolution state and thread ids, plus review bodies and conversation comments flagged `after_my_latest` by `watch-pr`'s rule; `respond` still lists the older ones as possibly answered, because one later reply of mine anywhere on the PR would otherwise hide every earlier summary). `scripts/post.py` posts one confirmed batch — an optional review, thread replies, one conversation comment, and resolutions — after checks that refuse the whole batch when the PR's head has moved past the batch's `head_sha`, an inline anchor is not a RIGHT-side diff line, a reply targets anything but a thread's first comment, a thread to resolve is someone else's, or a cited commit is not on the PR; `--dry-run` runs only the checks. The poster requires an attribution header but does not choose its text. The text lives in `.chezmoitemplates/posting-attribution.md`, which the skill renders with `includeTemplate ".chezmoitemplates/posting-attribution.md" . | trim` (the `trim` drops the file's trailing newline inside a code fence); a future posting skill for Jira or Slack includes the same partial so the line stays in one place. `references/posting.md` holds the batch schema and the anchoring rules. Queue discovery, head fetching, and posting used to be exposed as `list-review-requests`, `fetch-pr-head`, and `post-pr-review`; they are internal mechanics of this one discoverable workflow. Generic `create-worktree`, `launch-agent-in-pane`, and `herdr` remain separate because other dispatches use them.

The `jira` skill (`dot_agents/skills/jira/`) is the one way agents read and change Jira, and the posting skill for Jira comments. It is instructions only, with no scripts: it works through the Atlassian MCP server, which Claude reaches through the claude.ai Atlassian connector. Scripts over Atlassian's `acli` were tried first, on the model of `github-pr` over `gh`, and set aside for two reasons. `acli` failed inside the Claude Code sandbox even with every Atlassian host allowed (later traced to its OAuth credential, which the sandbox can't read), so it would have needed its scripts excluded from the sandbox. And `acli` lacks pieces a full skill needs: it can't list transitions, look up an account for a mention, or edit custom fields. The MCP server covers all of that, takes and returns Markdown (so the shared attribution partial goes in as it is), and reports the user's own account ID in every response. What it gives up is a script to enforce the checks `github-pr`'s poster does, so the stale check (re-read the issue's `updated` before applying) and the attribution line are instructions the agent follows. The skill names tools by their base names (`getJiraIssue`, `addCommentToJiraIssue`) because the prefix differs by harness and connector. It confirms two kinds of change differently: a message to people (a comment, or a created issue's summary and description) always needs the user's confirmation, while a change to the issue itself (a transition, a field edit, a link, a new issue) needs it unless the project's instructions, or a workflow following them, authorize that specific move — which is how `drive-implementation` can make the tracker moves a project's flow calls for without stopping each time. Nothing about a particular site is in the skill: the project's own `AGENTS.md` gives its site, project keys, workflow and pre-authorized moves, and custom-field IDs, and the skill discovers and confirms anything it needs that the instructions don't give. Codex and Gemini have no Atlassian MCP server configured yet; there the skill stops and says so. Wiring them is adding Atlassian's remote MCP server to each harness's config plus a one-time OAuth login per machine. The Herdr partial sends a dispatch's Jira key here too. That retired the `resolve-task` primitive, which fetched Jira keys over REST with `JIRA_*` environment variables: without Jira, all it did was try GitHub's PR endpoint before the issue endpoint, which the partial now says in one sentence.

The `summarize-github-pr` and `summarize-jira-ticket` skills summarize one PR or one Jira issue for a person getting oriented on it, and any agent can reach for them; `github-pr` opens every triage with the PR one. They stay general rather than shaped for a caller, to be tuned when a real use needs more. They exist as skills because triage sessions skipped a summary that was only a field in `feedback.py`'s output, going straight from the reviewer's hand-back to the first question; `github-pr` now spells out that the summary is printed before that question. The PR summary is metadata only, in a fixed shape: a two-row table of number and title (cut at 60 characters) over author and URL, then one bullet per review with its type and the number of comments it started, then the size and the PR it is stacked on (another open PR whose head is its base). What the PR changes is deliberately left out, because what I want from it is a consistent way to tell PRs apart, not a description. `scripts/summary.py` prints the markdown itself, so the skill runs inline and needs no model of its own; it skips the empty reviews GitHub records for each thread reply, for the same reason `watch-pr` does. The Jira summary uses the same table, with the issue's type before its key and the assignee in place of the author; an epic follows with its status, a bar of its children by status category (█ done, ▒ in progress, ░ to do) with their counts, and its unfinished children, and any other issue with its status, parent, linked PRs (found with `gh` by key as well, since a PR is often linked only through its branch name), blockers, and subtask count. Its `scripts/summary.py` reads Jira's REST API directly rather than through the MCP server, because speed is the point: a forked agent driving the MCP tools took 40 seconds to two minutes per epic, nearly all of it model turns, and an agent running bare `acli` reads still took about 15 seconds, while the script runs every read in parallel and returns in a couple of seconds. The caller passes the site with `--site` from the project's instructions, since a work site can't be hardcoded here. The token is scoped to reading (`read:jira-work` and `read:jira-user`), so a leak can't change anything; Atlassian accepts scoped tokens only through its gateway at `api.atlassian.com`, addressed by the site's cloud ID, which the script looks up from the site's public `/_edge/tenant_info`. The email and token come from `JIRA_EMAIL` and `JIRA_API_TOKEN` in the environment, set machine-locally rather than in these dotfiles. Reading the token from 1Password at run time was tried and set aside: a sandboxed `op` can't reach the 1Password desktop app even with its config and data folders readable and its `s.sock` socket allowed, so those sandbox loosenings were reverted. `acli` was tried first and set aside: inside the sandbox it reports itself unauthenticated, even with its hosts allowed, its config directory writable, and the keychain's Mach services reachable, and it gives no reason; excluding it from the sandbox works only for bare commands, which a script can't run. The `jira` skill's rule against reaching Jira any way but the MCP server is accordingly about changing Jira, which is what its confirmation and attribution protect.

The `chief-of-staff` persona keeps a small record of what I'm working on so it can draft two things on request: a standup update (a day or a week) and a summary of my year. It is deliberately minimal. An earlier version tracked everything — commitments owed in both directions, decisions, dispatched work across Herdr machines, an `index.md` roll-up, `update` and `briefing` rituals, a delegate-by-default rule, and a full link-hygiene discipline — and that machinery cost more to keep than the summaries were worth. The current design rests on one idea: **git history of the bundle is the retrospective**. Current work is plain files in `tasks/` with kebab-case names, so `ls tasks/` is the view of now and there is no roll-up to keep in sync. Each file is an Open Knowledge Format (OKF) concept, with `type` and `title` frontmatter and a matching H1 as its only required structure, kept because a uniform header lets each file read on its own at little cost per task. Starting something is creating its file. Finishing is two commits: first the task's outcome is written into the file, then the file is deleted. The split is what makes the rituals work, because the outcome text survives in history as the diff just before the deletion, where `git log -p tasks/` finds it. `projects/` holds long-lived context rewritten in place, and its files name the repositories that `standup` and `annual` cross-check with `git log` and `gh` to catch work that never got a task (and, for `annual`, to flag stretches where the record looks thin). Both rituals run only when asked and produce drafts. The bundle lives in the persona's working directory, with no configured path or fallback, and its own `AGENTS.md` wins over the persona on shape — layout, conventions, ritual details — because the same persona runs on work and home machines, and the work bundle tracks more than the home one. The `AGENTS.md` governs shape, not boundaries: never acting outward, never pushing the bundle, and never scheduling itself hold everywhere and can be loosened only by me in session, since a file the persona edits should not be able to widen its own permissions. The one part written from outside is `inbox/`: other agents drop notes there with the `add-to-inbox` skill, which writes to the directory named by `CHIEF_OF_STAFF_INBOX`; the persona triages each drop into a task or a project file at session start and deletes the raw note, treating it as another agent's claim rather than an instruction. `inbox/` is gitignored for the same reason. Links between files are bare `[[slug]]` wiki-links, and the bundle ships a `.marksman.toml` with `title_from_heading = false` so marksman binds them to filenames rather than to a file's H1. When I ask it to start an agent, it launches one into its own Herdr pane or worktree to talk to me directly and at most adds a task file; it doesn't relay or supervise. Claude and Codex both wrap the canonical prompt: Codex exposes it as `codex --profile chief-of-staff` and as a spawnable `[agents.chief-of-staff]` role. Self-scheduling is named as a non-goal because an earlier Claude wrapper created an hourly job that every instance raced to duplicate. There is no Gemini wiring yet.

The Claude wrapper carries a hook of its own, a `PostToolUse` on `Write|Edit` that puts every markdown file the persona writes through the `markdown-formatting` skill's `scripts/format-markdown --hook` (pinned prettier, `--prose-wrap never`). The bundle is nothing but markdown the persona rewrites all session long, and while it is now a git repository, a formatting hook at commit time was considered and rejected on friction: `prettier --write` modifying a staged file makes pre-commit fail the commit by design, so the persona would have to re-stage and retry every time formatting changed anything — and an agent facing a blocked commit is an agent tempted by `--no-verify`. Formatting at write time never blocks anything, which is what a bundle nobody reviews actually needs. Prettier's output is what those conventions already ask for — soft wrapping, `-` bullets, ATX headings, one blank line between blocks — and it leaves the reference-style links alone, so the hook mechanizes the persona's own style rather than imposing a second one. That skill's README argues against installing this hook globally, because a global formatter silently reflows other people's repositories that hard-wrap by convention, and says to opt in per project instead; binding it to the persona answers the same objection without a per-project step, since the only markdown this persona writes is its own bundle. There is no Codex counterpart. Codex hooks exist and a profile can carry them inline, but its `apply_patch` payload puts patch text in `tool_input.command` rather than a `file_path`, so the shared script would have to parse an envelope Codex owns and does not document — and would go back to silently doing nothing the day that envelope changed, because `--hook` swallows its own failures by design. An `apply_patch` matcher would also still miss markdown written through a shell heredoc. So the prompt keeps telling the persona to write the markdown correctly rather than pointing at a formatter: on Codex that discipline is still the only thing there is, and on Claude the hook is a backstop the persona is better off not counting on.

The bundle is live state the persona rewrites constantly, so chezmoi does not manage or seed it. On first use in a chosen working directory, the persona runs `git init` and creates the `.marksman.toml` its link scheme depends on and a `.gitignore` covering `inbox/` and `.DS_Store`; `tasks/`, `projects/`, and whatever else the bundle's `AGENTS.md` defines arise with their first entries, and `inbox/` arises when an agent first drops a note (the `add-to-inbox` script creates it if missing). Codex's ordinary `workspace-write` sandbox already grants access to that working directory, so the profile needs no extra writable root. Removing the former `dot_local/state/chief-of-staff/create_index.md` source deliberately does not add `~/.local/state/chief-of-staff/` to `.chezmoiremove`: existing live state is user data and must remain untouched. `.chezmoiremove` still deletes the persona's original `~/.claude/cos/` seed so that retired format does not linger on machines that applied it.

Model and concurrency choices come from the machine-local `agentBudget` datum. `.chezmoi.toml.tmpl` asks for `conservative` or `generous` during `chezmoi init` and defaults to `conservative`; consuming templates also fall back to conservative when the datum is absent or unrecognized. This keeps existing machines safe until their chezmoi config is regenerated or gains `agentBudget` under `[data]`. It sets the personas' models, and the model of the forked `implement` skill on Claude.

| Persona or skill  | Claude conservative / generous | Codex conservative / generous |
| ----------------- | ------------------------------ | ----------------------------- |
| Coordinator       | Sonnet / Opus                  | Terra medium / Sol high       |
| Chief of staff    | Sonnet / Opus                  | Terra medium / Sol high       |
| `implement` skill | Sonnet / Opus                  | the session's own model       |

The `investigate` skill stays on Sonnet on every machine, because its work does not benefit from a bigger model. Codex skills run on whatever model the current session uses; only the two personas have Codex profiles.

Codex caps spawned-agent threads at two for conservative machines and four for generous machines. These choices apply only to persona profiles and the subagent cap; the ordinary top-level Codex model remains the independently configured default.

The global harnesses do not include a persona. They keep Herdr dispatch and communication conventions available in ordinary sessions without forcing every session to coordinate. Codex's skills need no wiring because it reads `~/.agents/skills/` natively (see the Agent skills table above). A harness that needs its own global content adds it before or after the includes.

The harness files are `.tmpl`, not `.md`, so the `prettier` pre-commit hook (which runs with `proseWrap: never`) leaves their one-include-per-line layout alone; that layout matters because the render joins the sections with the blank lines between them. The section partials themselves are prose `.md` and stay prettier-managed. This is why there is no `agent-behaviors.md` wrapper partial: a `.md` composition file would get its include lines collapsed onto one line by prettier.

## Key tools configured

- **Shell**: zsh with starship prompt, zsh-autosuggestions, zsh-syntax-highlighting, direnv
- **Terminal**: Ghostty (ligatures disabled)
- **Prompt**: Starship — configured without Nerd Font glyphs, kubernetes module enabled
- **Git**: pull.rebase=true, rebase.updateRefs=true, rebase.autoSquash=true
- **AWS profile switching**: `aws-profile-login` / `aws-profile-logout` are zsh functions in `dot_config/kris-steinhoff/zshrc`, not scripts. They must be functions because they set `AWS_PROFILE` in the interactive shell — a standalone script would only mutate its own subprocess. `aws-profile-login` triggers SSO or static login if the current credentials are invalid, adding `--use-device-code` when `$SSH_CONNECTION` is set (a remote session with no local browser).
- **Scripts**:
  - `dot_local/bin/executable_ai-usage` — shows subscription usage for Claude and ChatGPT. A `uv run --script` Python tool that reads Claude Code's OAuth credential (`~/.claude/.credentials.json`, or the macOS Keychain) and Codex's ChatGPT credential (`~/.codex/auth.json`) and queries their respective usage endpoints. It adapts to the windows each account reports; `--service claude` or `--service chatgpt` limits the view to one provider. On a terminal it refreshes live in place until Ctrl-C, with Ctrl-R forcing a refresh. `--once` prints a single snapshot and exits, `--json` emits raw payloads keyed by provider, and `--json windows` emits every service's windows (key, percent used, length, reset time) and status in one shape for programs such as `choose-agent`, without failing on a service it can't read. Every mode reads through a shared per-service cache in `~/.local/state/ai-usage/`, so any number of callers (a status line, several live views) can run as often as they like without drawing 429s: a caller fetches only when the last attempt is older than its `--interval` (default 300), and a file lock makes concurrent stale callers wait for one fetch rather than each making their own. Failed attempts are cached too, so callers back off from an error together; a 429's Retry-After binds even Ctrl-R, since forcing through it only draws another 429. The cache holds the payload and the Claude plan name, never tokens.
