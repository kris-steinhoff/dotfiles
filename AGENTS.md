# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a personal dotfiles repository managed with [chezmoi](https://chezmoi.io/). This repo is the chezmoi source directory — files use chezmoi naming conventions (`dot_` prefix for dotfiles, `executable_` prefix for scripts) and are applied to `$HOME` by chezmoi.

## Bootstrap

To set up a new machine:

```bash
chezmoi init kris-steinhoff/dotfiles
chezmoi apply
```

`chezmoi init` clones this repo to `~/.local/share/chezmoi`. `chezmoi apply` copies managed files to `$HOME` and runs `run_once_bootstrap.sh`, which:

1. Ensures `~/.zshrc`, `~/.config/git/config`, and `~/.vimrc` each source/include the shared config files under `~/.config/kris-steinhoff/`
2. Runs `brew bundle install` from `~/.config/homebrew/Brewfile` if Homebrew is available
3. Runs `nvim --headless "+Lazy! restore" +qa` to install Neovim plugins at the commits pinned in `lazy-lock.json`

## Neovim plugin pinning

`dot_config/nvim/lazy-lock.json` is checked in. lazy.nvim installs plugins at the commits recorded there, which guards against supply-chain compromise of upstream repos. The bootstrap step above installs from the lockfile rather than letting plugins float to HEAD.

When updating plugins:

1. Run `:Lazy update` inside nvim.
2. Review the diff in `~/.config/nvim/lazy-lock.json`.
3. `chezmoi re-add ~/.config/nvim/lazy-lock.json` to pull the new commits into the source dir, then commit.

Without step 3, the next `chezmoi apply` will revert the lockfile to whatever's checked in.

## Claude Code settings.json

Other tools write into `~/.claude/settings.json`. Orca and Herdr each install their agent-state hooks there (Orca's alone span about fifteen hook events), and Claude Code adds keys of its own, such as a flag recording an accepted prompt. A plain template wiped all of that on every apply, so the source is a `modify_` script, `dot_claude/modify_private_settings.json.tmpl`, like the one for Codex's `config.toml` described below. The settings we manage live in the partial `.chezmoitemplates/claude-settings.json.tmpl`, which the script embeds. The script reads the live file and writes the partial merged over it. A top-level key in the partial replaces the live value wholesale, and a live key the partial lacks is kept. Hooks merge per hook group: a group that runs any managed command is replaced by the managed groups, and every other group belongs to another tool and stays, after ours. The script tells a group apart only by its commands, so a hook taken out of the partial goes into its `RETIRED_COMMANDS`; otherwise it would linger as another tool's. It is plain Python with no dependencies, because macOS's own `python3` is enough and uv adds nothing here.

Herdr's own `SessionStart` entry is one of those kept groups. These dotfiles used to manage a copy of it with a `~` path, which Herdr's install didn't recognize as its own, so the live file ended up with two. The managed copy is retired, and Herdr owns its entry outright.

Claude Code also rewrites the file in its own key order whenever it changes something internally (e.g. saving a permission), so both sides are kept in `jq -S` order:

- The partial must render in `jq -S` order, which the local `sort-claude-settings-json` pre-commit hook checks by rendering it with `chezmoi execute-template`. It checks rather than fixes, because a template isn't JSON that `jq` can rewrite. The script's output is in the same order.
- `~/.claude/settings.json` (the live file) is kept sorted by a `ConfigChange` hook, `dot_claude/hooks/executable_sort-settings-json.sh`, which re-sorts it with the same `jq -S` after every change.

A `chezmoi apply` diff on this file should therefore only mean a real value changed.

The partial is a template for one reason: a machine can add its own sandbox write paths. A list named `claudeSandboxAllowWrite` under `[data]` in the machine's chezmoi config is appended to `sandbox.filesystem.allowWrite`. This is how a work project's paths reach the sandbox without being written into these dotfiles, for example a beads database in a project folder that sessions in every clone and worktree need to lock. User settings are the right level for that rather than a project's `.claude/settings.local.json`, because a worktree session loads its own checkout's settings, not its clone's. `.chezmoi.toml.tmpl` carries the list forward, so a later `chezmoi init` doesn't drop it.

Herdr's agent-state hooks are Herdr's, and these dotfiles don't manage them. `herdr integration install <agent>` writes each one (Claude's is `~/.claude/hooks/herdr-agent-state.sh`), and Herdr rewrites it on upgrade, flagging an outdated or missing one in its settings' Integrations tab. Managing Claude's copy here meant a copy-back commit after every Herdr upgrade, and until then `chezmoi apply` stopped to ask about the changed file. The `settings.json` entry that runs the hook is Herdr's as well, and the `modify_` script for that file keeps it (see above), so a new machine gets the hook when the Claude integration is installed from Herdr. The hook's source was deleted without a `.chezmoiremove` entry, since that would delete the live file Herdr still needs.

## Codex config.toml machine-local state

Codex rewrites `~/.codex/config.toml` at runtime and injects machine-local state that must not be version-controlled: `[projects.*]` trust levels (per-machine checkout paths), `[tui.*]` UI counters, and `[hooks.*]` trusted hook hashes. A plain template would clobber that state on every apply and force re-trusting projects and hooks.

So the source is a chezmoi `modify_` script, `dot_codex/modify_private_config.toml.tmpl`, rather than a static template. A `modify_` script receives the current target on stdin and its stdout becomes the new file. The script is a `uv`-run Python program that parses the live file with `tomlkit`, sets only the settings we manage (`model`, `project_doc_fallback_filenames`, `approval_policy`, `approvals_reviewer`, `[features]`, `[sandbox_workspace_write].writable_roots`, `[agents]` — the last templated on `agentBudget`), and dumps the document back. Because `tomlkit` preserves the layout of everything it does not touch, Codex's machine-local tables round-trip verbatim, applies are idempotent (a clean machine shows no diff), and nothing is silently dropped whatever new keys Codex may add. This needs `uv` present at apply time (it is in the Brewfile); the earlier `awk`-based version avoided that dependency but classified sections by regex and could drop unknown top-level bare keys.

The shebang pulls `tomlkit` via `uv run --with tomlkit`, not PEP 723 inline metadata (`--script`). This matters because `uv run --script` keys its ephemeral venv on the script's file path, and chezmoi runs a `modify_` script from a fresh temp path on every apply — so that env never hit the cache and uv reinstalled the dep (printing `Installed 1 package`) on every `chezmoi apply`. A `--with` env is keyed on its requirements instead, so it survives the changing paths and uv only rebuilds (and reports) it on a cold cache or a dep bump. The tradeoff is that this script alone differs from the PEP 723 pattern `ai-usage` uses.

The filename attribute order is `modify_private_` (type prefix before the `private_` permission attribute); `private_modify_` is not recognized and chezmoi treats the leftover `modify_` as a literal filename.

## Herdr app settings

The Herdr desktop app (`herdr-app`) keeps its whole interface as files in `~/.config/herdr-app/`, and its Settings screen writes `settings.json` itself (zoom, appearance, contrast, telemetry). So that file's source is a chezmoi modify-template, `dot_config/herdr-app/modify_settings.json`, which reads the live file and sets only the keys we manage, as the `modify_` scripts above do; it needs no interpreter because chezmoi's own `fromJson` and `setValueAtPath` are enough. The app ships no Tokyo Night, so `themes/tokyo-night.json` is ours; the app leaves theme files it didn't write alone. Keys stay on the app's defaults, and the shipped layouts and mods are left unmanaged, because Herdr replaces them on every start and personal changes to them go through clones. The older terminal Herdr's `~/.config/herdr/config.toml` is a separate program's config and stays as it is.

## Config architecture

Shared configs live under `dot_config/kris-steinhoff/` (deployed to `~/.config/kris-steinhoff/`) and are _included_ by the machine-local config files (not replaced). This lets local overrides coexist with the shared baseline:

| Shared file                          | Included by            |
| ------------------------------------ | ---------------------- |
| `~/.config/kris-steinhoff/zshrc`     | `~/.zshrc`             |
| `~/.config/kris-steinhoff/gitconfig` | `~/.config/git/config` |
| `~/.config/kris-steinhoff/vimrc`     | `~/.vimrc`             |

The `run_once_bootstrap.sh` script uses `ensure_config` to add the include line automatically, prompting the user when a file already exists but doesn't include the shared config.

## Agent skills

Load `dot_agents/skills/AGENTS.md` before adding, editing, or removing any skill; it covers how a skill is authored once and deployed to every agent surface. Before changing a skill, also read the `AGENTS.md` in that skill's own directory (`dot_agents/skills/<name>/`, or `dot_claude/skills/<name>/` for a Claude-only skill) if it has one; it holds the reasons the skill is built as it is. chezmoi deploys none of these files.

## Global instructions and personas

Claude and Codex each read a single always-loaded instruction file (`~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`). Shared global content lives in chezmoi template partials under `.chezmoitemplates/`, so one edit updates every surface that includes it:

- **`delegation.md`** — the entry layer for running agents elsewhere: recognize a plain-language "run `<agent>` on `<task>` in a worktree or session" without a slash command, resolve the task source, seed the agent with context and outcome rather than a method, name artifacts for their downstream consumer, report back and tear down only when asked, and act-on-clear/confirm-on-doubt. It is kept to about 2KB because every session loads it. It names no workspace tool: an agent uses whatever its harness offers for worktrees, sessions, or subagents, and plain `git worktree` for checkouts, because a sandboxed session can't reach Herdr's or Orca's sockets. It reads a Jira task key with `jira`, settles a GitHub number as PR or issue by trying `gh pr view` before `gh issue view`, and routes GitHub PR review requests to `github-pr`, which owns their grouping and repeated queue runs.
- **`communication.md`** — how to write for a human who has an AI agent at hand: lead with the conclusion, explain references instead of pointing, favor judgment over exhaustive precision, write the current state rather than the revision history, and describe existing work neutrally. It also sets how to ask the user anything: yes/no may stay in prose, an either-or never does (it becomes multiple choice or a yes/no on the recommendation), everything else is multiple choice with the recommendation first, and several questions go in dependency order — a question whose options another answer could change waits for that answer, and the independent ones are batched (in the harness's structured question tool, or as numbered questions with lettered options). It carries the posting rule: agents post messages to people on the user's behalf only through a skill built for that kind of posting (today `github-pr`, which owns its confirmation, attribution, and posting for both reviews and the author's replies, and `jira` for Jira comments), and where no skill covers the target they draft the message for the user instead. Adding a posting skill is what grants the permission, so the rule itself needs no edit per target.

Each harness file is a thin `.tmpl` that includes the section partials that apply to it, one `{{ template ... }}` line per section:

| Harness                     | Sections included                              |
| --------------------------- | ---------------------------------------------- |
| `dot_claude/CLAUDE.md.tmpl` | `delegation` + `communication` + `claude-code` |
| `dot_codex/AGENTS.md.tmpl`  | `delegation` + `communication` + `codex`       |

`claude-code.md` holds Claude Code mechanics that would be noise elsewhere. So far that is how to drive AskUserQuestion: use it for every multiple-choice question, overriding the tool's own description, which says to save it for decisions that block the agent. That override is why the section exists: the tool description pulls the other way, and the harness-neutral rule alone did not reliably win against it. It goes further for every stop that waits on me: even a lone yes/no or a manual step goes through AskUserQuestion, because Herdr shows a session in that prompt as blocked while a prose question looks the same as a finished agent. This applied only inside Herdr at first; it is unconditional now, so the rule no longer depends on which workspace tool is running. A command I'm to run with `!` is shaped differently: an open question holds the input line, so a `Done` button meant dismissing it to type the command. The question asks only whether I'll run it, and on `I'll run it` the agent ends its turn with the command as its whole message, then checks the command's output itself when it arrives. The command used to go in a message before the question, and in 25 of 35 such questions across my transcripts the agent went from reasoning straight to the question with no message at all, so the question said "run the command above" over nothing; in three more it wrote a message without the command. The last message of a turn is reliably shown, the same lesson the `summarize-github-pr` skill taught (see its `AGENTS.md`). A `PreToolUse` hook on AskUserQuestion that refused the question until a `! ` line had been written was set aside, because the hook can't see it: a message's text is not yet in the transcript when its tool call runs. It also says that sandbox-excluded commands leave the sandbox only when run bare: a pipe or redirect silently puts them back, and xcodebuild then fails with a `permissionDenied` that doesn't mention the sandbox. Agents piped xcodebuild into `grep` out of habit, which is what kept iOS tests failing in one project. If the prose doesn't break that habit, a `PreToolUse` hook rejecting a piped or redirected excluded command is the stronger fix. Last, it tells Claude to pipe a CLI's JSON to `jq` rather than to an inline script, the one rule kept from the retired `cli-json` skill.

`codex.md` is the Codex counterpart, and so far holds one rule: a command that failed in the sandbox for a reason a retry won't change runs escalated from then on, on its first call. One Codex session ran three repository gates sandboxed, watched each fail on the network, reran it escalated, and did the same again for every round of changes, `make typos` three times over. The same session is why the `modify_` script grants Codex's sandbox the uv and npm caches Claude's sandbox may already write: without them Codex pointed each tool at a cold cache under `$TMPDIR`, which needed the network to fill.

Coordinator behavior is opt-in. Two personas remain, `coordinator` and `chief-of-staff`, with one canonical prompt each under `.chezmoitemplates/agents/personas/`. Claude Code agent files under `dot_claude/agents/` add YAML frontmatter and include the shared prompt; the same definition works as a subagent and as a primary persona through `claude --agent <name>`. Specialist work (implementing, reviewing) is done by skills rather than personas, because a skill carries the same prompt to every harness without a per-harness wrapper and the coordinator can call it when it needs a specialist.

Codex uses one profile for both entry points. `dot_codex/<name>.config.toml.tmpl` deploys a launch profile selected with `codex --profile <name>`, while the `modify_` script for `config.toml` registers that same file under `[agents.<name>].config_file` so another Codex session can spawn it. Rewriting the whole `[agents]` table on each apply also drops registrations for personas that no longer exist.

The `coordinator` carries one piece of frontmatter the chief-of-staff doesn't: a `PostToolUse` hook (`dot_claude/hooks/executable_coordinator-delegation-nudge.sh`) that nudges it back toward delegating. It exists because the persona drifted into doing substantial multi-file work inline — one session ran ~20 edits across a bug fix and a full stack rebase without a single hand-off — and the prose rubric alone didn't hold. The hook reads the running transcript, counts the inline edits (`Edit`/`Write`/`NotebookEdit`) since the last delegation (an `Agent`/`Task` call, or a `Skill` call to `implement`, `review`, or `github-pr`), and the first time that run reaches three with no hand-off injects a one-time reminder to declare whether the next phase belongs with an implementor. A delegation resets the run, so a coordinator that hands off is never nagged; it fires once per run rather than on every edit past the threshold, so a legitimately-inline stretch costs at most one reminder; and it is non-blocking and fail-open (any error exits 0 with no output). Binding it through the agent's own frontmatter — rather than a global hook self-gating on the payload's `agent_type` — keeps it firing only while `coordinator` is the active agent, primary or subagent; it is a Claude Code mechanism, with no equivalent on the Codex profile. One caveat: it relies on the `PostToolUse` `additionalContext` field reaching the model, which is not guaranteed on every Claude version — if a firing never lands, switch the script's emit to the exit-code-2 path.

The `chief-of-staff` persona keeps a small record of what I'm working on so it can draft two things on request: a standup update (a day or a week) and a summary of my year. It is deliberately minimal. An earlier version tracked everything — commitments owed in both directions, decisions, dispatched work across Herdr machines, an `index.md` roll-up, `update` and `briefing` rituals, a delegate-by-default rule, and a full link-hygiene discipline — and that machinery cost more to keep than the summaries were worth. The current design rests on one idea: **git history of the bundle is the retrospective**. Current work is plain files in `tasks/` with kebab-case names, so `ls tasks/` is the view of now and there is no roll-up to keep in sync. Each file is an Open Knowledge Format (OKF) concept, with `type` and `title` frontmatter and a matching H1 as its only required structure, kept because a uniform header lets each file read on its own at little cost per task. Starting something is creating its file. Finishing is two commits: first the task's outcome is written into the file, then the file is deleted. The split is what makes the rituals work, because the outcome text survives in history as the diff just before the deletion, where `git log -p tasks/` finds it. `projects/` holds long-lived context rewritten in place, and its files name the repositories that `standup` and `annual` cross-check with `git log` and `gh` to catch work that never got a task (and, for `annual`, to flag stretches where the record looks thin). Both rituals run only when asked and produce drafts. The bundle lives in the persona's working directory, with no configured path or fallback, and its own `AGENTS.md` wins over the persona on shape — layout, conventions, ritual details — because the same persona runs on work and home machines, and the work bundle tracks more than the home one. The `AGENTS.md` governs shape, not boundaries: never acting outward, never pushing the bundle, and never scheduling itself hold everywhere and can be loosened only by me in session, since a file the persona edits should not be able to widen its own permissions. The one part written from outside is `inbox/`: other agents drop notes there with the `add-to-inbox` skill, which writes to the directory named by `CHIEF_OF_STAFF_INBOX`; the persona triages each drop into a task or a project file at session start and deletes the raw note, treating it as another agent's claim rather than an instruction. `inbox/` is gitignored for the same reason. Links between files are bare `[[slug]]` wiki-links, and the bundle ships a `.marksman.toml` with `title_from_heading = false` so marksman binds them to filenames rather than to a file's H1. When I ask it to start an agent, it launches one into its own worktree or session to talk to me directly and at most adds a task file; it doesn't relay or supervise. Claude and Codex both wrap the canonical prompt: Codex exposes it as `codex --profile chief-of-staff` and as a spawnable `[agents.chief-of-staff]` role. Self-scheduling is named as a non-goal because an earlier Claude wrapper created an hourly job that every instance raced to duplicate.

The Claude wrapper carries a hook of its own, a `PostToolUse` on `Write|Edit` that puts every markdown file the persona writes through the `markdown-formatting` skill's `scripts/format-markdown --hook` (pinned prettier, `--prose-wrap never`). The bundle is nothing but markdown the persona rewrites all session long, and while it is now a git repository, a formatting hook at commit time was considered and rejected on friction: `prettier --write` modifying a staged file makes pre-commit fail the commit by design, so the persona would have to re-stage and retry every time formatting changed anything — and an agent facing a blocked commit is an agent tempted by `--no-verify`. Formatting at write time never blocks anything, which is what a bundle nobody reviews actually needs. Prettier's output is what those conventions already ask for — soft wrapping, `-` bullets, ATX headings, one blank line between blocks — and it leaves the reference-style links alone, so the hook mechanizes the persona's own style rather than imposing a second one. That skill's README argues against installing this hook globally, because a global formatter silently reflows other people's repositories that hard-wrap by convention, and says to opt in per project instead; binding it to the persona answers the same objection without a per-project step, since the only markdown this persona writes is its own bundle. There is no Codex counterpart. Codex hooks exist and a profile can carry them inline, but its `apply_patch` payload puts patch text in `tool_input.command` rather than a `file_path`, so the shared script would have to parse an envelope Codex owns and does not document — and would go back to silently doing nothing the day that envelope changed, because `--hook` swallows its own failures by design. An `apply_patch` matcher would also still miss markdown written through a shell heredoc. So the prompt keeps telling the persona to write the markdown correctly rather than pointing at a formatter: on Codex that discipline is still the only thing there is, and on Claude the hook is a backstop the persona is better off not counting on.

The bundle is live state the persona rewrites constantly, so chezmoi does not manage or seed it. On first use in a chosen working directory, the persona runs `git init` and creates the `.marksman.toml` its link scheme depends on and a `.gitignore` covering `inbox/` and `.DS_Store`; `tasks/`, `projects/`, and whatever else the bundle's `AGENTS.md` defines arise with their first entries, and `inbox/` arises when an agent first drops a note (the `add-to-inbox` script creates it if missing). Codex's ordinary `workspace-write` sandbox already grants access to that working directory, so the profile needs no extra writable root. Removing the former `dot_local/state/chief-of-staff/create_index.md` source deliberately does not add `~/.local/state/chief-of-staff/` to `.chezmoiremove`: existing live state is user data and must remain untouched. `.chezmoiremove` still deletes the persona's original `~/.claude/cos/` seed so that retired format does not linger on machines that applied it.

Model and concurrency choices come from the machine-local `agentBudget` datum. `.chezmoi.toml.tmpl` asks for `conservative` or `generous` during `chezmoi init` and defaults to `conservative`; consuming templates also fall back to conservative when the datum is absent or unrecognized. This keeps existing machines safe until their chezmoi config is regenerated or gains `agentBudget` under `[data]`. It sets the personas' models, and the model of the forked `implement` skill on Claude.

| Persona or skill  | Claude conservative / generous | Codex conservative / generous |
| ----------------- | ------------------------------ | ----------------------------- |
| Coordinator       | Sonnet / Opus                  | Terra medium / Sol high       |
| Chief of staff    | Sonnet / Opus                  | Terra medium / Sol high       |
| `implement` skill | Sonnet / Opus                  | the session's own model       |

Codex skills run on whatever model the current session uses; only the two personas have Codex profiles.

Codex caps spawned-agent threads at two for conservative machines and four for generous machines. These choices apply only to persona profiles and the subagent cap; the ordinary top-level Codex model remains the independently configured default.

The global harnesses do not include a persona. They keep delegation and communication conventions available in ordinary sessions without forcing every session to coordinate. Codex's skills need no wiring because it reads `~/.agents/skills/` natively (see `dot_agents/skills/AGENTS.md`). A harness that needs its own global content adds it before or after the includes.

The harness files are `.tmpl`, not `.md`, so the `prettier` pre-commit hook (which runs with `proseWrap: never`) leaves their one-include-per-line layout alone; that layout matters because the render joins the sections with the blank lines between them. The section partials themselves are prose `.md` and stay prettier-managed. This is why there is no `agent-behaviors.md` wrapper partial: a `.md` composition file would get its include lines collapsed onto one line by prettier.

## Key tools configured

- **Shell**: zsh with starship prompt, zsh-autosuggestions, zsh-syntax-highlighting, direnv
- **Terminal**: Ghostty (ligatures disabled)
- **Prompt**: Starship — configured without Nerd Font glyphs, kubernetes module enabled
- **Git**: pull.rebase=true, rebase.updateRefs=true, rebase.autoSquash=true
- **AWS profile switching**: `aws-profile-login` / `aws-profile-logout` are zsh functions in `dot_config/kris-steinhoff/zshrc`, not scripts. They must be functions because they set `AWS_PROFILE` in the interactive shell — a standalone script would only mutate its own subprocess. `aws-profile-login` triggers SSO or static login if the current credentials are invalid, adding `--use-device-code` when `$SSH_CONNECTION` is set (a remote session with no local browser).
- **Scripts**:
  - `dot_local/bin/executable_ai-usage` — shows usage for Claude, ChatGPT, and OpenRouter. A `uv run --script` Python tool that reads Claude Code's OAuth credential (`~/.claude/.credentials.json`, or the macOS Keychain) and Codex's ChatGPT credential (`~/.codex/auth.json`) and queries their respective usage endpoints. It adapts to the windows each account reports; `--service` (repeatable) limits the view to the named providers. OpenRouter is prepaid credits rather than a subscription, so its panel shows the account's balance, a bar per budget enforced on the key, and the key's spend today, this week, and this month. Its keys come from the environment, set machine-locally like the Jira token: `OPENROUTER_API_KEY` for the key's spend and budgets, and `OPENROUTER_MANAGEMENT_KEY` for the balance, because OpenRouter's balance endpoint accepts only a management key, which can also create and delete keys. Either one alone is enough, and a machine with neither hides the panel. Because sign-in can differ between callers when it comes from the environment, a missing credential is never written to the shared cache, so a caller without the keys can't hide OpenRouter from one that has them. On a terminal it refreshes live in place until Ctrl-C, with Ctrl-R forcing a refresh. `--once` prints a single snapshot and exits, `--json` emits raw payloads keyed by provider, and `--json windows` emits every service's windows (key, percent used, length, reset time) and status in one shape for a script that compares them, without failing on a service it can't read. Every mode reads through a shared per-service cache in `~/.local/state/ai-usage/`, so any number of callers (a status line, several live views) can run as often as they like without drawing 429s: a caller fetches only when the last attempt is older than its `--interval` (default 300), and a file lock makes concurrent stale callers wait for one fetch rather than each making their own. Failed attempts are cached too, so callers back off from an error together; a 429's Retry-After binds even Ctrl-R, since forcing through it only draws another 429. The cache holds the payload and the Claude plan name, never tokens. Run inside the Claude sandbox, it needs to reach `api.anthropic.com`, `chatgpt.com`, and `openrouter.ai` and to write that cache; `settings.json` grants all of them.
