# Herdr app settings

This file covers which of the Herdr desktop app's files these dotfiles manage and why; load it before changing anything in this directory.

The Herdr desktop app (`herdr-app`) keeps its whole interface as files in `~/.config/herdr-app/`, and its Settings screen writes `settings.json` itself (zoom, appearance, contrast, telemetry). So that file's source is a chezmoi modify-template, `modify_settings.json`, which reads the live file and sets only the keys we manage, as the `modify_` scripts for Claude's and Codex's settings do; it needs no interpreter because chezmoi's own `fromJson` and `setValueAtPath` are enough. The app ships no Tokyo Night, so `themes/tokyo-night.json` is ours; the app leaves theme files it didn't write alone. `keys.json` is managed the same way as `settings.json`, by `modify_keys.json`, which adds cmd-shift-o to open the plan mod's picker. Herdr upgrades its default shortcuts only in a keys file nobody has touched, so adding a key means new defaults from later releases have to be added by hand, as the template does for 0.1.16's cmd-m (minimize) and cmd-a (select all in a terminal); check each release's notes for more; the template writes nothing when there is no file yet, since a file holding only our key would replace every default. The shipped layouts and mods are left unmanaged, because Herdr replaces them on every start and personal changes to them go through clones.

`layouts/personal.json` is that kind of clone: the shipped `main` layout copied with one difference: its bottom bar (the `status` block) becomes a `status-row` row holding that block, the `reviews-badge` block, and an `ai-usage` block at its right end. It is a snapshot, so changes Herdr later makes to `main` don't reach it; to pick them up, re-copy `main.json` and make the change again. The block shows `mods/ai-usage/`, which runs `~/.local/bin/ai-usage --json windows` every minute, whenever the script's cache folder (`~/.local/state/ai-usage/`) changes, and when clicked. That is cheap because the script's shared cache decides when the providers are actually asked (see `dot_local/bin/AGENTS.md`). Watching the cache keeps the block in step with the live view, which re-reads the cache every second: without it, a fetch the live view made, or its Ctrl-R, reached the block up to a minute later. Each service is one unlabeled glyph of nested rings, one per limit window with the longest inside, painted with gpui-kit's `PathBuilder` so any percent draws in theme colors; hovering names the service and gives the numbers. Color goes by pace rather than the raw percent, because a high weekly figure late in the week is normal while a modest 5-hour figure early in the window is the real warning. The mod takes pace from the script's `ahead_of_pace` and the color from its `level` rather than computing them, so the rings and the live view's bars always agree (definitions and reasons are in `dot_local/bin/AGENTS.md`). Pace is how far a window is ahead of the even rate that reaches 100% exactly at the reset, the measure the retired `choose-agent` skill used for backpressure but without its 90% headroom, so the color is exact: any amount ahead means on track to run out, and turns the ring yellow; 10% of the window ahead, or the limit itself, turns it red. The theme has no orange, so the `high` level, which the live view shows in orange, shows in yellow. The tooltip shows how long until the window is back on pace with no further use. A layout block can't size itself to its content, so the mod measures its content and resizes its own block's width to fit; clicking it switches to the tab named "AI usage" if one exists, else opens one running the live `ai-usage` view. `programs.json` gives that terminal its own name and icon (`mods/ai-usage/icon.svg`); without the entry Herdr, which looks through uv to the script it runs, finds no `ai-usage` program and shows uv's icon.

The bottom bar also holds `reviews-badge`, which shows `mods/reviews/`, a GitHub review queue. The same mod runs in two places, told apart by its props. The badge copy runs `~/.local/bin/github-review-queue --all` every five minutes for each GitHub repo a local space is in (see `dot_local/bin/AGENTS.md` for what counts as reviewed; `--all` because the mod also needs the reviewed PRs, to keep one listed while its session works or waits on me and to keep its mute), puts the result in shared state, and reads "Reviews: <n>", the number of PRs the Reviews tab lists, with a red dot in front while a review session needs the owner. At zero it stays visible as a dim "Reviews", so the Reviews tab is always one click away. The mod reads no files from the `github-pr` skill; starting `/github-pr review <n>` is its only tie to it.

The copy in a Reviews tab lists the PRs of every repo in one list, each with its repo under its number, in an order picked from its Sort menu (oldest first by default, from the queue's `created_at`; the choice is shared state, `reviews.sort`), with a terminal pane split beside it as a viewer. Each review's Claude session, `/github-pr review <n>`, runs in the repo's main checkout as a herdr-core terminal with no tab of its own (`hc run --bg --no-parent`), which keeps the tab bar from growing a tab per PR. Its `herdr-reviews.*` labels (repo, number, title) are how the mod finds it again, and because the queue keeps no state of its own, finding it is what stops a second session reviewing the same PR. Clicking a row shows its session in the viewer with `terminal.show`. A tab-less session gets none of Herdr's attention cues, so the badge copy notifies when one turns blocked or finished, and puts the number of blocked sessions on Herdr's Dock icon with `setBadge`. There is no close button: the badge copy kills and removes a session once its PR has left the list (reviewed at its head, merged, closed, or no longer asked) and the agent isn't working or waiting on the owner. It acts only on a queue it read itself since starting, and only for repos whose read succeeded, so a failed read or a stale queue from before a restart never closes a session; an abandoned one can be ended with `/exit` in the viewer. Right-clicking a row opens the same mod as a popup menu (`props.menu`) with Mute and Open on GitHub. A muted PR drops, in greys only, to a Muted group at the bottom and stays out of the badge's count and Review all, with no Review button of its own; mutes live in shared state (`reviews.muted`) and last until unmuted or until the PR leaves the queue of a repo that was read, so a failed read never forgets them. A PR that someone besides me and its author has already reviewed (the queue's `other_reviewers`, which leaves out bots) is muted automatically the first time the poller sees it that way. The exception is a PR that asks me for review by name rather than through a team (the queue's `requested_directly`): it is never muted automatically, an automatic mute made before the request arrived is lifted, and its row says "asked of you by name" beside who else reviewed it. `reviews.automuted` maps each PR muted that way to whether the mute is still the automatic one, so it happens only once (an unmute sticks, even after more reviews arrive) and the row can say why it's muted: "already reviewed by …" for an automatic mute, "muted by you" once I've muted or unmuted it by hand. That record is pruned the same way as the mutes. Sessions aren't started with `--rm`, so one that dies at launch stays in `hc ls --all` to be inspected until its PR leaves the list. `DEMO` at the top of `main.js` swaps the queue for made-up PRs, for trying the interface; sessions are real either way.

`mods/plan/` shows a local plan in a Plan tab the way the claude.ai plan page does: progress, Needs attention, approach, done-check, the PR stack, collapsible task cards, and the journal. cmd-shift-o (`mod.open:plan`) opens the same mod as a picker of the plans in the focused space's repo, found through the git common dir so a linked worktree finds the main checkout's `.plans/`, and a folder or slug can be typed instead. The picker opens the plan in a tab of its own (`props: { plan: <folder> }`), because the page's layout needs a tab's width, or selects the tab already showing it. That tab is named for the plan's folder and found again by that name, since `panes()` doesn't expose a mod pane's props. Edit `find.js` for finding plans and their tabs, `main.js` for the picker, and `plan.js` and `plan-view.js` for the Plan tab.

The mod doesn't start or track drivers. `/drive-implementation` runs in any tab, it starts its agents as `hc` sub-agents (`dot_agents/skills/drive-implementation/`), and Herdr already marks a driver waiting on a question as blocked, so a panel that started each driver in a space and checkout of its own and showed every agent's status from `hc` labels was more machinery than the work needed.

The Plan tab reads the plan's files itself rather than through `plan-store`, since the files are the store's documented layout and a refresh then starts no process, and rereads them when `watchFolder` reports a change, with a 30-second timer behind it, because on Linux `watchFolder` skips git-ignored folders and `.plans/` is ignored. It is read-only: a local plan's driver asks its questions in its own session with the structured question tool, which Herdr shows as blocked, so an open question offers a button to the driver instead of a form; a view that wrote would go through `plan-store --as herdr`. The driver is the live terminal running an agent whose `plan.driver` label is the plan's folder, which `/drive-implementation` has it set; a tab's shell outlives the agent run in it, so a terminal without its agent doesn't count. `plan.js` repeats the page's derived views (when a running plan counts as blocked, the PR chain, answered questions folded into the journal, and the dependency graph's layout), so a change to the guide's schema or to how the page shows a plan needs the same change there. The graph's edges are painted with gpui-kit's `PathBuilder` and `window.paint_path`, the calls the ai-usage rings use, and its tasks are positioned boxes. The layout follows the page: the title and progress stay pinned at the top, and below them, when the tab is wide enough, the graph has its own scrolling column on the left of the plan, standing in for the page's sticky side column; narrower, a button in the header shows it above the plan. Picking a task in the graph highlights its chain, and picking its id also scrolls to its card and highlights the card briefly. A gpui-kit scroll handle can bring only a direct child of its scroll area into view, so the plan's column is a flat list of blocks with each task card its own block, rather than sections nesting their contents. The highlight is an overlay whose opacity fades out, since opacity, size, and position are all gpui-kit animates. A plan page has no Plan tab, since the mod can't read an artifact's database. `demo.js` holds a made-up plan's documents, and with `DEMO` on in `main.js` the picker opens it in a real Plan tab.

`herdr-app check` runs a mod's `init()` for real, so the reviews mod stops polling (`polls()`) and ai-usage stops before its first fetch while `checking()` is true; otherwise a check would read the review queue, write shared state, close review sessions, or ask the AI providers. The plan mod only reads, so it needs no guard. A check also writes `gpui-kit.d.ts` and `jsconfig.json` into a mod folder it checks. Delete them rather than committing them, because chezmoi would deploy them to `~/.config/herdr-app/mods/`.

The app replaced the terminal Herdr (`herdr`) for daily use. The terminal version's `~/.config/herdr/config.toml` (source `dot_config/herdr/config.toml.tmpl`) is a separate program's config, kept for occasional use, and the nvim blocks keyed on `HERDR_ENV` and `HERDR_PANE_ID` run only there: the app sets `HC_TERMINAL_ID` instead, and names panes from `programs.json` and the program it sees running.
